# 投注页与订单明细个人比赛备注 Planning

日期：2026-10-13，2026-10-15 完成实现与验收。
依据：`2026-10-13-投注页比赛备注编辑-RESEARCH.md` 与用户确认。

## 目标与范围

- 投注 card 时间左侧排列“官方备注 icon（有值时）→ 个人备注 icon（始终）→ 时间”。官方只读；个人有值蓝色、无值灰色，hover/focus 展示、点击编辑。
- 订单“明细”不增加每场比赛时间，在现有比赛标题区域、队伍名称旁接入上述备注组件；包括已支付、已结账、过期比赛，允许编辑本人备注，不变更订单投注、倍率、命中或结账状态。
- 个人备注由当前登录账号拥有，以标准化比赛 ID 保存；同账号同比赛跨订单与投注页共用一份当前备注。
- 不随公共比赛更新、7 天缓存清理而丢失；未登录/本地游客点击提示登录。导入导出本次不包含个人备注，不增加个人备注历史版本页面、离线编辑或自动删除任务。

## 数据模型与迁移

新增 `app/match-notes.ts` 提供独立类型、限制、ID/文本校验及按 revision 合并的纯函数：

```ts
type PersonalMatchNote = {
  matchId: string;
  note: string;
  revision: number;
  updatedAt: string;
};
type PersonalMatchNotes = Record<string, PersonalMatchNote>;
```

不向公共 MatchItem、SavedSlip 或公共比赛缓存添加个人字段。缺记录返回 `{note: '', revision: 0, updatedAt: ''}`；前端用加载状态区分未加载/加载失败与真实空备注。

在 `db/schema.ts` 新增 `userMatchNotes`，新增顺序 migration（目前最大编号 0006，预计 `0007_user_match_notes.sql`，实现时再次核对）：

| 字段 | 约束 |
| --- | --- |
| user_id | NOT NULL，外键 users.id，ON DELETE CASCADE |
| match_id | NOT NULL，与 user_id 组成主键 |
| note | TEXT NOT NULL DEFAULT '' |
| revision | INTEGER NOT NULL DEFAULT 0 |
| updated_at | TEXT NOT NULL |

不对 shared_matches 建级联外键，不回填旧数据，个人备注记录即使清空也保留并增加 revision。无需额外 match_id 单列索引：读取始终先以 user_id 限定，再按 ID 集合查找。保持项目现有迁移登记方式，核对 journal 与迁移工具，不改已发布 migration。

## API 与并发策略

新增 `app/server/match-notes-service.ts`、`app/api-client/match-notes.ts`：

| 接口 | 请求 | 响应 |
| --- | --- | --- |
| GET `/api/users/me/match-notes?ids=...` | 最多 100 个 ID，归一化去重；不允许无条件列出全部记录 | `{notes: PersonalMatchNote[]}`，请求 ID 无行也返回空状态 |
| PATCH `/api/users/me/match-notes/[matchId]` | `{note: string, expectedRevision: number}` | 原子保存产生的 PersonalMatchNote |

所有路由复用 `requireAuthenticatedCloudAccount`，userId 仅取会话，不接受客户端 userId；成功和错误响应均加 `Cache-Control: private, no-store`。401 登录提示，400 参数错误，409 备注版本冲突。规范 ID 即可保存，不要求共享比赛仍存在，以支持历史明细。

ID 校验：trim 后调用 `normalizeSportteryMatchId`；非空、最长 128 字符，禁止控制字符；兼容数字官方 ID、旧前缀与 `match-${Date.now()}-${index}` / `sample-${index}` 等已有本地 ID，不以数字正则误拒绝历史导入数据。用绑定参数与 encodeURIComponent，不拼接 SQL。读取分批 100 场，避免超长 URL。

文本规则：原始输入最多 2000 个 JS UTF-16 code units（与 Input maxLength 口径一致），去除首尾空白、保留内部换行，空白成为空备注；revision 必须是非负安全整数且强制传入。错误字段（包括 userId）拒绝，备注仅以纯文本展示。

写入采用数据库单语句条件 UPSERT，不先读后无条件写：缺行仅允许 expectedRevision=0 创建 revision=1；已有行仅在 revision=expectedRevision 时更新并递增。可用 INSERT SELECT 的“expectedRevision=0 或目标行存在”条件限制插入，再由 ON CONFLICT WHERE 控制更新，避免缺行且 expectedRevision>0 时错误创建。实现时用真实 SQLite 验证首次并发创建和 UPDATE 分支，不仅断言字符串。

通过 `RETURNING` 返回本次写入的版本（或同等原子结果），不保存后另读可能已被下一次写覆盖的记录；未写入返回 409 与当前 revision，沿用 routeError 可序列化的字段。本功能为单条备注写入，无新增订单批量事务。

## 前端状态与数据流

1. FootballRoute 新增备注读取/保存回调，保存复用 enqueueWrite 管理同步状态与 401。回调捕获调用账号，执行前与响应后验证账号仍一致；不让旧账号排队任务在新会话下执行。
2. 独立 `usePersonalMatchNotes` hook 由 FootballApp 当前账号挂载实例使用，负责内存映射、加载/error 状态、100 场批量读取、去重请求、重试、revision 合并。不写 localStorage/sessionStorage、不进入 cloudPersonal 序列化或比赛/订单快照。
3. 投注页对当前渲染比赛 ID 批量补读；打开订单明细时对明细比赛批量读取。已有缓存可先显示，明细重开与页面数据刷新可重验证，跨设备变化无需实时推送。
4. 官方/兜底刷新只更新 matches，个人映射保留。PATCH 返回仅更新备注映射，不 setMatches 覆盖整个比赛。旧 GET 不覆盖更高 revision；重复读取和保存响应均校验账号/挂载代次。
5. 游客不请求私人 API，个人 icon 默认灰色，点击调用现有登录入口。独立 HTML 的默认登录回调为空：为备注组件提供明确的“请到云端页面登录后编辑”提示和已有云端链接，避免点击无反应。
6. 账号切换/登出由 FootballApp account key 重建清空映射和编辑草稿，hook cleanup 中断/忽略旧请求；请求失败保留已知备注并允许重试，未知版本时不能保存。

## 复用 UI 组件

新增 `app/components/MatchNotes.tsx`（可按职责拆分），统一官方 Tooltip 与个人编辑器，供 MatchCard 和 orderDetail Drawer 使用。个人状态/保存回调来自同一 hook，防止两入口显示不同版本。

- Popover 多行文本框、字数统计、保存/取消；初次打开从已加载版本初始化草稿，存 editorExpectedRevision；后续刷新不重置正在编辑的草稿。
- 保存立即独立 PATCH，未变化禁用保存。取消/外部关闭丢弃未保存草稿；提交期间禁止再次保存和关闭，失败保持草稿并显示错误。
- 409 保留草稿，显示“备注已在其他位置更新”，提供重新读取当前值；读取后重新初始化编辑版本，由用户再次编辑/保存，不静默覆盖。
- 保存成功立即同步图标颜色、Tooltip 与同 ID 的另一入口；清空成功变灰，与官方 icon 无关联。
- 已结账 Drawer 的结果锁定提示补充“个人备注可独立编辑”；备注按钮不受 orderHitsSaving、matchFailed 或 settledAt 的禁用规则影响。
- 桌面及手机保持投注页时间组不挤压比赛编号；明细标题区域的备注按钮不挤压队伍名称、赛果标签与失败勾选，必要时标题内容换行，不新增时间行。Tooltip 长文本保留换行，Popover 宽度受视口限制。新增样式限制在专用 class，避免现有 `.detail-match-title span` 通配样式改变备注颜色。
- 键盘 focus/Enter 可打开个人编辑器，灰/蓝状态辅以 aria-label；官方 icon 与个人便签/编辑 icon 区分，个人 Popover 打开时关闭其 Tooltip。

## 验证与验收

服务测试使用两个本地账号和同一 matchId：互不读写、伪造归属无效；首次创建、并发首次创建、后续 CAS、清空后陈旧保存、非法版本/ID/长度、失败不改变已有行。旧行不存在默认空；删除共享比赛不影响个人表；本功能不修改订单或 finance 表。

异步/纯函数测试覆盖归一化、分批去重、旧 GET 不覆盖保存结果、账号切换丢弃旧响应、保存过程中比赛刷新仍保留备注；公共比赛与订单缓存/导出没有新增私人字段。既有比赛 service 测试/集成用本地 D1 验证官方与赛果更新后私人记录不变。

浏览器用桌面约 1440px 与手机约 390px：

1. 无/有官方备注时显隐正确，个人始终可见；空/保存/清空对应灰/蓝/灰，纯文本与换行正常。
2. 保存、取消、外部关闭、网络失败重试、409、加载失败与登录失效；保存后刷新、重新登录仍保留。
3. 筛选/排序、新比赛刷新及历史明细均按正确 ID 读写；两个账号切换无串内容。
4. 已过期/已支付/已结账订单明细能读写备注，关闭重开仍存在；订单 updatedAt、投注、倍率、命中、财务不因备注操作变化。
5. 同一比赛出现于投注页和不同订单，展示同一账号当前备注；另一个账号默认空。
6. “载入投注/复制投注”的可售限制保持原行为；通过明细查看历史备注，无需载入。
7. 公共快照 POST 和比赛导出无个人备注；控制台无新错误、无横向溢出。
