- 不预填历史累计值，金额默认留空；零值、空值、非有限值、超精度或超安全金额拒绝提交。
- 实时预览“当前总额 → 本次 ±金额 → 调整后总额”，同时可显示累计纠错调整前后。保存按钮明确写“确认增加 / 确认减少”；提交期间禁用重复操作，失败保留草稿。
- 例：订单支出 1,000，原累计纠错 +20，总额 1,020；本次减少 5，保存后累计纠错 +15，总额 1,015。减少支出会增加利润，增加收入也会增加利润。
- 历史按实际创建顺序倒序、按类型筛选、分页：记录时间（上海时区）、归属日期（或“无日期／初值”）、类型、本次差值、累计纠错前后、备注、来源。补录旧日期仍是最新创建的记录；前后值指创建顺序的累计纠错，不代表该生效日的历史余额。无需把当前订单总额冒充为历史总额；如展示操作时总额，必须明确其为当时快照。
- 手机使用接近全宽的弹窗和纵向记录卡片；桌面可用表格。记录按需加载，不拖慢订单列表。

## 历史、补差与撤销

- 已确认：旧累计纠错直接作为无日期初值；分别标记收入纠错和支出纠错。非零值形成只读历史余额记录，负值原样保留；零值无需生成记录。备注注明“升级前累计值，原始明细不可追溯”。迁移时间不冒充原创建时间，UI 可显示“历史迁移，原时间未知”。
- 已确认：已入账记录不直接编辑或删除，备注也随记录固定；填错追加同类型调整，保留审计过程。
- 收入误填 +200，实际应为 +180：追加“收入 −20”即可，属于收入纠错，不能填成支出 +20；后者虽利润相同，却把收入和支出都虚增了。支出误填 +200 同理追加“支出 −20”。
- 已确认记录操作提供“补差”快捷入口：预选原类型、原归属日期（原记录无日期则仍为空），金额留空，展示关联原记录。例中用户填写 −20，备注可写“原收入纠错 200，实际 180，补差 −20”。这不修改原记录，不自动推断新的最终目标。
- 普通新增无需关联；从原记录发起补差时带 adjusts_entry_id，仅用于追溯，不改变金额计算。同一条可多次部分补差，不能沿用“只能冲销一次”的限制。重复提交仍由 requestId 防重。
- 若要完全抵消，追加相反数即可。首版建议仅提供同一套“补差”表单，不另加一键冲销，避免多次补差后的剩余金额难以理解。
- 原记录不因订单被撤回、删除或筛选而消失。

## 已确认的日期与趋势口径

- 创建时间 created_at：系统记录操作实际发生时间，用于流水排序和追溯；归属日期 effective_date：用户可选，决定趋势归属。两者不能混用。
- 无日期纠错：和旧历史余额一起累计为初值，影响所有日期的累计曲线，不计入任何一天的当日收入／支出。默认不选日期，因此新纠错也可调整初值。
- 有日期收入纠错：带符号 delta 加到所选日的收入；有日期支出纠错：带符号 delta 加到所选日的支出。当天收入、支出、利润和累计值均体现该纠错；税额仍仅来自订单，不随纠错增减。
- 计算：当日收入 = 当日订单税后收入 + 当日收入纠错；当日支出 = 当日订单支出 + 当日支出纠错；当日利润 = 当日收入 − 当日支出。累计值 = 无日期初值 + 截至该日的全部对应事件。
- 当日净收入或净支出允许为负（如当天只有收入补差 −20），不可截断为零；新增提交仍校验全局对应总额不为负。是否限制任一历史时点累计余额非负不在现有约束中，建议不追加此限制。
- tooltip 显示订单金额、纠错差值、当日合计及累计值；不要仅列独立纠错而遗漏当日收入／支出的总值。全局统计包含所有纠错，订单筛选盈亏继续只包含订单。
- 查询日期范围前的有日期纠错需预累加；范围后的纠错不计入该范围累计值。SQL 日期分组使用 effective_date，不是 created_at。总纠错汇总表仍包含有日期与无日期全部金额，趋势基线只能取无日期合计，避免双计。
- 补差应默认沿用原归属日期：原 +200 属于 10 月 20 日，补 −20 也选 10 月 20 日，该日净纠错为 +180；若改选今天，则表示原日 +200、今天 −20；若不选日期，则初值 −20、原日 +200。三者全局净额一样，历史曲线不同，提交前需要显示清楚。
- 类型误选的更正：在原类型、原日期追加相反数，再在正确类型和日期新增正确金额。不将一条收入记录直接改成支出。
- 日期校验复用 `isFinanceTrendDate`，保持上海日历日语义。建议允许过去及今天、禁止未来日期：未来纠错若立即进入全局总额，会使截至今天的趋势与当前统计不一致；若延后入账则需新增计划状态，超出当前模型。已获开发者确认，客户端禁选并由服务端再次校验。
- 仅有无日期余额、没有任何日期事件时：显示“初值”摘要；曲线如需单个展示点，可用查询日期或今天作展示锚点，明确该点不代表归属日期，不能把日期写回流水。合计为零但仍有操作记录时，记录列表仍正常展示。
- 无筛选范围时曲线覆盖订单与有日期纠错的联合日期范围；任意用户筛选范围的末点不要求等于全局总额，只有覆盖全部事件时核对一致。

## 游客与完整 JSON 备份恢复（已确认同做）

### 已核实的额外约束

- `app/personal-sync.ts` 的旧同步模型虽含 finance，但当前 `FootballRoute.syncOrders` 只走订单 API，删除、批量更新、新建分多次请求执行，再读取财务；不能直接把现有完整导入当作原子恢复机制。
- 云端订单列表可能分页，完整导出不能只序列化当前已加载订单；新增流水也是分页查询，必须获取同一快照下的全部记录。
- 因此本次完整备份恢复需要专门服务端入口，不应在浏览器串行调用普通订单和纠错接口拼装，否则失败后会留下半套订单与账本。

### 本地与格式

- 已确认游客和云端同时支持同一交互、类型、正负差值、可选日期、备注和记录规则，以及完整备份导出／导入恢复。
- 游客升级时由本地总额减本地订单合计推导无日期历史余额，保留原总额；本地基线、流水和订单建议使用同一版本化快照或可原子提交的本地事务存储，不能因多 key 分别写入而账实不符。持久化失败不提示成功；处理重复迁移与多标签页冲突。
- 完整备份格式提升为 v6（实施前复核版本占用），包含完整订单、设置、财务基线与流水，以及原有比赛数据范围。流水包含稳定来源 ID、类型、差值、可空归属日期、原创建时间、备注、关联关系；汇总总额用于校验，不能作为第二份金额再次累计。
- 区分目标系统的本地记录 ID 与稳定来源 ID；跨账号导入不信任文件中的 user_id、revision、权限、当前账号 ID。原创建时间仅作导入来源信息，实际导入时间另记；导入记录不伪装成目标账号当时的在线操作。
- 设置／订单单独导出不携带财务流水。普通订单导入只通过订单变动影响总额，不额外注入纠错。完整导入才处理备份中的账本。

### 导出一致性

- 服务端提供完整个人备份快照能力，覆盖所有订单和所有当前有效账本记录；获取一致快照或用版本校验并在数据变化时重试，不拼接不同时间的分页结果。
- 明确业务范围：个人订单、设置、账本一致恢复；公共比赛属于共享数据，沿用权限隔离，不能由普通账号完整备份恢复覆盖公共库。公共比赛若包含在文件中，应单独授权、单独展示结果，不声称与个人事务共同原子提交。
- 游客从已持久化的一致本地快照导出。原有归属日期和负数差值原样保留，初值与日期流水不能被扁平化为单个余额。

### 完整覆盖恢复（已确认纳入范围）

- 覆盖后当前有效订单、设置、初值和有日期纠错按文件恢复，从而恢复原总额和历史曲线；先校验订单计算口径与文件汇总一致，不接受无法解释的差额。
- 当前账本历史不物理删除：建议引入账本档案／代次（ledger generation），原代次归档，新代次装载备份流水并激活。普通记录只追加规则仍成立，覆盖恢复是单独记录的恢复事件，不是编辑原纠错。
- 当前记录默认查看有效代次，提供“归档账本”只读查看；恢复事件记录来源、时间和数量。汇总、趋势和默认导出只计当前有效代次，避免归档金额重复入账。完整备份是否携带归档可独立定义，首版建议明确只恢复当前有效账本，操作归档留在目标端。
- 原备注、类型、归属日期、来源关系保留；目标本地 revision 由目标系统生成，不能复用文件 revision。导入前后值按重放顺序重建，原值若保留仅作来源快照。
- 需要新增代次实体、当前代次引用或等效结构；流水、汇总、revision 和恢复事件在同一事务中切换。原历史基线记录在有效代次中只计算一次。

### 完整合并（已确认纳入范围）

- 订单继续按订单 ID 合并；纠错按稳定来源命名空间 + 来源记录 ID 去重，重复导入不重复累计，不能按金额、备注、日期等内容猜测两笔是否相同。
- 同稳定 ID、相同内容跳过；同稳定 ID、不同内容拒绝并报告冲突，不静默覆盖。补差关系按导入映射重连；关联记录缺失时拒绝损坏备份，不能关联到别人的记录。
- 不同来源的无日期历史余额不能盲目相加：合并预览中单列“迁移历史初值”，默认保留当前历史余额，不合入无法证明独立性的备份历史余额。预览可明确选择使用备份历史余额，以追加无日期调整记录实现差额替换，不删除当前记录；该操作也需要稳定来源标识与幂等保护。合并预览展示新增、跳过、冲突、历史初值策略和预计总额。
- 必须区分“旧系统迁移历史余额”和“升级后手动新增的无日期纠错”：后者有独立记录 ID，和有日期纠错一样按 ID 合并，不能因为无日期而全部跳过。历史初值策略只针对不可拆分的迁移余额。
- 只在稳定来源记录首次出现时计入；同一记录重复导入保持当前目标记录，不重复重放金额。若备份历史余额曾被选择忽略，后续再次导入仍要明确显示其状态，不能作为普通新纠错自动计入。
- 不依赖文件 hash 做流水去重：备份增加一笔记录后整个 hash 会改变。文件摘要可用于请求校验，不能替代稳定来源 ID。

### 旧 v5 文件兼容

- 旧文件只有总额：覆盖时用文件总额减去文件订单合计，生成对应类型的无日期历史余额；不生成有日期明细或虚构旧备注。总额为非负、差额可为负。
- 合并旧文件时默认保留目标账本初值，仅合并订单，因为无法证明旧总额与目标是否重复。预览明确“此文件无纠错明细，未合并财务初值”；如用户需恢复旧账本，使用完整覆盖。
- 旧客户端绝对值 PATCH 转换为无日期差值流水，并保留版本校验，不绕过新账本。

### API、事务与失败处理

- 建议新增个人备份导出和导入预览／提交接口，按登录用户隔离；预览返回校验结果、策略、数量、预计金额、备份摘要及相关资源版本。最终命名在 Planning 确定。
- 提交携带 requestId、导入策略（合并／覆盖）、历史初值选择、原始备份或已验证的暂存标识、预览版本与摘要；服务端重新验证，不信任客户端计算结果。合并时订单、设置、新流水及汇总变更属于同一恢复边界；覆盖时订单、设置、账本代次装载与激活属于同一恢复边界。revision 或订单集合变化则整批 409，不部分成功。
- 预览后有新订单创建也必须能检测，单独检查文件中旧订单的 updatedAt 不足以发现新增；需要个人数据版本或等效集合快照 guard，所有相关写入都必须参与约束。
- 处理 D1 事务／请求大小上限：可采用不可见的暂存导入数据加最终原子激活，不能分批直接修改线上有效数据后宣称原子。明确可支持的文件容量并在提交前校验；具体容量根据实际运行约束在 Planning 确定，不猜固定限额。
- 相同请求重试只恢复一次；失败保留原有效订单和账本；账号切换后不应用旧请求结果。游客采用同等快照校验与原子切换语义。

## 最终确认结论

已确认并纳入方案：

- 原订单统计位置保留入口，弹窗填写和查看记录；收入／支出类型、正负差值，备注可选且最多 200 字。
- 日期默认空；无日期计初值，有日期计对应日收支；禁止未来日期；旧余额按原类型作为无日期历史初值。
- 记录只追加，记录旁增加“补差”入口，自动带出原类型与原日期，用户填写本次差值并关联原记录。
- 游客与云端同做，完整备份导出、合并导入和覆盖恢复一起做。
- 合并时纠错记录按稳定来源 ID 去重，同 ID 内容冲突时拒绝；升级后的手工无日期纠错与有日期纠错同样按记录 ID 合并。不可拆分的迁移历史余额默认保留当前值，在预览中单独选择是否使用备份历史余额。
- 覆盖恢复采用“归档当前账本、装载并激活备份账本”的代次方案，同时恢复金额和日期曲线；归档历史只读可查，不参与当前汇总、趋势或默认导出，避免重复入账。
- 旧 v5 备份覆盖时由文件总额减文件订单合计，恢复为对应类型的无日期历史初值；旧 v5 合并不自动叠加财务初值。
