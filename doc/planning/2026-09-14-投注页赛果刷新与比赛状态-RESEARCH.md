# 投注页赛果刷新、比赛取消与 remark Research

## 需求边界

- 分析投注页点击“刷新数据”后出现大量赛果相关请求的原因，给出批量化、去重和请求时机优化方案。
- 已经进入本地/云端共享比赛缓存、但在计划开赛前从官方当前比赛列表消失的比赛，按需求标记为“已取消”；2041458 是当前实例。
- 保存官方比赛的 `remark`，非空时在投注页比赛 card 右上角、开赛日期左侧显示 info icon，hover/focus 显示完整备注。
- 本阶段只做 Research，不修改业务代码、数据库或发布版本。

## 现有刷新与赛果数据流

### “刷新数据”主链路

1. `FootballApp.refreshSportteryData()` 调用 `/api/matches/refresh`。
2. 服务端 `refreshMatchesFromOfficial()` 使用两分钟刷新锁和一分钟手动冷却，取得官方快照后写入 `shared_matches.data_json`。
3. 09:00–11:00 的 morning 模式取完整 `getMatchListV1`，然后对列表中每一个 matchId 并发 6 个请求 `getFixedBonusV1`。
4. 11:00–23:00 的 standard 模式同时取 `getMatchListV1` 和批量 calculator，但列表分支仍会先对所有保留比赛逐场请求 fixed-bonus，calculator 只用于覆盖同场的详细赔率。
5. 前端合并新快照后，投注页自动赛果 effect 会对当前筛选且已展开的“已停售且缺完整赛果”比赛发起 `getUniformMatchResultV1` 批量请求。

### 两类容易被混淆的请求

- `getFixedBonusV1` 是逐场 fixed-bonus/赔率详情接口。当前主要使用它的 `oddsHistory`、五种玩法赔率、让球和单关信息；响应虽也含 `isCancel/matchResultList`，但不能用“批量赛果”直接替代它的赔率职责。
- `getUniformMatchResultV1` 已经是按日期批量赛果接口。当前大量请求不是因为仍在逐场拉赛果，而是批量分页大小被 UI 筛选缩小、缺少提前结束，且“取消”未被识别为终态。

## 根因分析

### 1. 批量赛果已存在，但 `pageSize` 选错了口径

- 自动赛果 effect 以当前 UI `filteredMatches` 在日期区间内的数量作为 `pageSize`。
- 批量接口的 `total/pages` 却是该日期区间内所有官方赛果，不受页面的联赛、销售状态、日期筛选或折叠状态限制。
- 因此页面只显示 1 场时会以 `pageSize=1` 请求；以 2026-09-14 的官方数据为例，立即变成 11 页/11 次请求。
- 这个口径也让筛选器成为网络分页参数，切换筛选后的请求数不稳定。

### 2. 已找到全部候选时仍继续翻页

- 每页结果会按标准化 matchId 映射回候选，找到完整比分后从 `unresolvedIds` 删除。
- 循环条件只看 `pageNo <= totalPages`，没有在 `unresolvedIds.size === 0` 时提前结束。
- 即使目标在第 1 页已获得完整比分，仍会把其余页全部请求完。

### 3. “取消”被当作未完赛，会反复扫全部分页

- 批量 parser 只会从 `sectionsNo1/sectionsNo999` 解析数字比分。`sectionsNo999="取消"` 得到空 `values` 和空 `fullScore`。
- 页面处理遇到空比分直接 `return`，不会从 `unresolvedIds` 移除 2041458，也不会改变销售状态。
- 扫完所有页后，它被按“unfinished”调度：10 分钟后重试，最多 3 次重试（初次外再 3 次）。
- 在“页面只剩 1 场、当日官方 11 条、2041458 为取消”的极端但真实场景下，理论上是 `11 页 × 4 轮 = 44` 次批量赛果请求。

### 4. 自动赛果候选以“计划开赛”而非“预计完赛”为边界

- `getMatchSaleState()` 在计划开赛时刻到达后立即返回 `stopped`。
- 自动赛果 effect 对所有 `stopped && !hasCompleteMatchResult` 的可见已展开比赛请求赛果，因而会在球赛刚开始时就查询，而不是等常规时间结束。
- 如果实际开球延迟，用户会看到还未真正开赛的比赛进入赛果 loading；即使准时开球，也会在比赛进行期间进行无效轮询。

### 5. 比赛快照刷新又有一类独立的逐场过量请求

- `fetchSportteryFixedBonusPayloadMap()` 对传入列表中的每个 ID 请求 fixed-bonus，只限并发数 6，没有按销售阶段或有效 pool 筛选。
- 2026-09-14 现场列表是 54 场，因此一次真正官方刷新会发出 54 个 fixed-bonus 请求，其中 44 场仍是 `Define`。
- 当日只有 12 场比赛的 `poolStatus` 非空（10 场 `Selling` + 2 场 `OddsIn`），其余 42 场没有可用 pool；实测其中一场的 fixed-bonus 五类历史列表全空。
- 这类请求是为了赔率详情，不是投注页批量赛果 effect；但它确实在点击“刷新数据”时发生，也应一并降频。

### 6. 同一 fixed-bonus matchId 会跨刷新轮次重复请求

- 单次快照内已有两层去重：输入 ID 使用 `Set`，正在请求的同一 ID 使用 `inFlightFixedBonusRequests`；standard 模式也会把列表分支的成功响应复用给 calculator 分支。
- 但 `inFlightFixedBonusRequests` 会在请求结束后立即删除，没有已完成响应的短时结果缓存。进入投注页、自动刷新、手动刷新或云端失败后前端官方兜底，只要开启了新的快照轮次，就会再次请求同一 matchId。
- standard 模式中，如某个列表 fixed-bonus 请求失败、未写入共享 map，calculator 分支还会在同一轮对该 ID 重试一次。
- 云端刷新如已返回“带错误的旧快照”，前端现在会主动抛错并再直连官方接口；这会绕开服务端公共缓存/锁，在云端本轮已发出部分 fixed-bonus 请求的失败路径上再发一轮。
- 因此，重复出现 `matchId=2041512` 不是赛果批量接口在逐场调它，而是该场一直被放进每一轮 fixed-bonus 全量补充。它当前没有任何可用赔率历史，是首批应过滤的候选。

### 7. 缓存合并把“开赛前从官方消失”回退为待开售

- `mergeSportteryMatchCache()` 保留 7 天内本地/云端旧比赛。
- 旧比赛未出现在新快照时：已到计划开赛时间就标记 `stopped` 并清选择；未到开赛时间则无条件标记 `pending` 且保留选择。
- 因此 2041458 这类“旧快照有、官方完整列表已无、且还未开赛”的比赛被错误展示为“待开售”。

### 8. `remark` 在类型和转换层丢失

- 官方 `SportteryMatch` 通过索引签名容忍未声明字段，但没有显式定义 `remark`。
- `convertSportteryMatches()` 构建 `MatchItem` 时只保留 ID、销售状态、日期、场次、联赛、时间、队名和玩法，未拷贝 `remark`。
- `MatchItem` 也没有 `remark`，因而它不会进入 React 状态、浏览器缓存或 D1 `data_json`。
- D1 的比赛主体本来就是 JSON，添加可选字符串不需要数据库迁移。

## 推荐修复方向

### A. 先修正批量赛果调度（高优先级）

1. 将批量赛果 `pageSize` 与 UI 筛选数解耦，固定请求已验证的服务端上限 100；仍以响应中的 `pages/total/pageSize` 校验后续分页。
2. 每页按 ID 应用后，若 `unresolvedIds.size === 0` 立即结束当前日期区间，不请求无关后续页。
3. 增加批量记录终态解析，至少区分 `completed | cancelled | unfinished`。`sectionsNo999="取消"` 是 `cancelled`，要从 unresolved 删除、禁止重试，但不应伪造 `0:0` 或空 `MatchResult`。
4. 将自动赛果候选判定抽为可测的 `isAutoResultEligible(match, now)`，不再把“已到计划开赛时间”直接当作“应该有赛果”。推荐默认在计划开赛后 120 分钟才进入赛果队列，再保留现有未完赛退避作为延迟/中断的容错。
5. 将分页扫描和终态分类从 React effect 抽到 `app/sporttery.ts` 或独立纯函数模块，使 pageSize、提前结束、取消和缺失候选可直接单测。

以 2041458/当日 11 条的现场数据计算，前三项可将当前最坏 `44` 次降为 `1` 次：第一页就识别取消，立即终止，不重试。

### B. 将已取消建模为独立销售状态

1. `MatchItem.saleStatus` 从 `pending | selling | stopped` 扩展为 `pending | selling | stopped | cancelled`；代码中已广泛使用 `cancelled` 英式拼法表示取消标志，建议业务状态也统一使用 `cancelled`。
2. 显式官方信号优先：批量赛果 `sectionsNo999="取消"` 或 fixed-bonus `isCancel=1` 都应将比赛标记 `cancelled`。
3. 按用户指定的缺失规则：一场比赛已在共享缓存中，成功获得的官方完整 `getMatchListV1` 不再包含它，且当前时间早于计划开赛时间，则标记 `cancelled`。
4. 缺失推断必须只在“完整列表成功”时启用。当 `getMatchListV1` 失败、代码只用 calculator 的可售子集兜底时，不能把未在 calculator 中的几十场未售比赛批量误判为取消。
5. 建议在 `SportteryMatchSnapshot` 增加一个仅用于合并的“完整列表/本次官方观测 ID”信号，或在服务层明确传入可推断取消的 ID 集合；不要把“所有 incoming 缺失”无条件改为取消。
6. `cancelled` 必须是不可选状态，当前投注草稿中该场已选项应清除，避免被继续计入注数和奖金；不修改已保存订单的结算规则。
7. `getMatchSaleState()` 应先于开赛时间返回 `cancelled`，避免原定开赛时间过后又被降级为 `stopped`。`isMatchSelectable`、日期可用性、更多玩法弹窗、手动补单下拉和销售状态筛选要同步处理。
8. 云端比赛使用 `shared_matches.data_json`，新状态可直接随整个 `MatchItem` 保存，不需要 D1 迁移；导入校验的状态白名单需同步扩展。

### C. 降低比赛快照中的逐场 fixed-bonus 请求

推荐先做不改变接口语义的保守降频：

1. 只对官方列表中至少有一个有效 pool 阶段（例如 `Selling`/`OddsIn`）或已有非空赔率的比赛获取 fixed-bonus；对所有 pool/odds 全空的远期 `Define` 比赛不发请求。
2. 对未请求 fixed-bonus 的比赛，保留官方列表已给出的基础信息，并在后续刷新中一旦 pool 进入 `OddsIn/Selling` 再获取完整赔率。
3. 按当日实际返回，这一保守筛选可将 fixed-bonus 从 54 次降至约 12 次，降少约 78%，同时保留已进入赔率录入/销售阶段比赛的完整玩法。
4. **不按是否开赛过滤 fixed-bonus**：它还承担赛前赔率、让球和单关信息；只保留“有效 pool/赔率”这个筛选条件。“开赛 + 120 分钟”只用于批量赛果调度。
5. 云端返回不带错误的共享快照时直接使用；若返回带 `refreshError` 的旧快照，说明本轮未取得可用官方列表，仍需保留浏览器直连兜底。生产验收已确认 Worker 存在无法取得官方完整列表的情况，而 fixed-bonus 候选过滤可避免兜底重新放大为 54 场全量请求。
6. 进一步的可选优化是：主 card 优先使用列表/calculator 批量给出的当前赔率，只在用户展开“更多玩法”或赔率历史时懒加载 fixed-bonus。这能继续降请求，但会改变待开售比赛的首屏数据完整性，建议不与本次修复捆绑。

### D. 保存并展示 `remark`

1. 在 `SportteryMatch` 和 `MatchItem` 增加 `remark?: string`，转换时执行 `trim`；空字符串可省略，非空值保留官方原文。
2. 现有快照合并、浏览器 JSON 缓存、云端 `data_json`、`clearMatchSelections` 都是对比赛对象整体展开/拷贝，只要转换层保留字段就会自动持久化；不需要迁移。
3. 同一 matchId 后续官方 `remark` 变更时以新快照覆盖；比赛本次从官方列表缺失时保留旧 `remark`，便于已取消/已停售 card 继续说明原备注。
4. `MatchCard` 将右上角调整为“可选 info icon + 开赛日期”容器；只有 `remark.trim()` 非空才渲染 `InfoCircleOutlined`，`Tooltip` 展示完整原文。
5. icon 应支持鼠标 hover 和键盘 focus，并增加包含备注的 `aria-label`；移动端保留 Ant Design Tooltip 的触控打开能力。

### E. 已取消 card 展示

- `MatchCard` 增加 `cancelled` class 和“已取消”标签，整张 card 使用浅灰背景；队名、日期和赔率降低视觉强度。
- 已取消不应显示赛果 loading，不应参与自动赛果重试，也不可继续选择玩法。
- “更多玩法”弹窗和手动补单的比赛状态文案也要显示“已取消”，不能落入现有的默认“已停售”分支。

### F. 支付前对已取消比赛做第二次确认

1. 不改变订单赛果判定、中奖计算、结账和账本逻辑；仅在未支付订单进入现有 `payOrders()` 前增加风险提示。
2. 不能只看订单创建时保存的 `order.matches[].saleStatus`，因为它可能还是旧状态；应按标准化 matchId 与当前共享比赛快照交叉，只检查订单中实际已选的比赛。
3. 单笔支付和一键批量支付都经过同一个包装函数；现有第一次“确认支付”保留，如检出已取消比赛，再弹出一个 Modal，列出影响订单数和比赛，用户选择“仍然支付”才调用原 `payOrders()`。
4. 已取消比赛在投注页默认被隐藏，但仍保留在完整 `matches` 状态/共享快照中，因此订单页付款检查不受默认筛选影响。

## 更优的中期架构建议

当前比赛列表刷新由服务端做公共锁和 D1 共享，但投注页批量赛果仍由每个浏览器标签页直接请求官方，然后回写共享比赛。多用户/多标签页会重复请求同一日期区间。

建议在完成本次低风险修复后，再将“批量赛果拉取 + 取消终态合并”移到 `matches-service` 的官方刷新锁内，或增加独立的服务端赛果刷新锁。这样一轮官方请求只有一个服务端执行者，其它用户直接读共享 D1。该改造需要考虑定时刷新频率、锁超时、批量结果局部失败和 Cloudflare 执行时间，不建议未经 Planning 直接捆入本次 UI 修复。

## 数据、兼容和风险

- `saleStatus="cancelled"` 和 `remark` 都位于 `MatchItem` JSON，旧数据没有字段时依旧按现有逻辑运行，不需要 D1 迁移或历史数据批量重写。
- 仅依据“未出现在 incoming”推断取消有高风险：官方列表请求失败后 calculator 兜底本来就只有可售子集。必须带“完整官方列表已成功”前提。
- standard 模式会按业务日过滤列表。取消推断应与原始 `getMatchListV1` 的实际 ID 集合对比，不能只与过滤后的 `matches` 对比，否则凌晨仍未开赛的上一业务日比赛可能被误判。
- 取消状态不应生成 `MatchResult`，否则后续订单判定可能把空值或伪比分当成真实赛果。
- 已确认不修改已保存/已支付订单的取消结算口径；本次只在支付前对存在已取消场次的订单增加额外确认。
- 订单快照的状态可能落后于共享比赛，支付警告必须使用当前比赛集按 ID 匹配；否则新增 `saleStatus` 也会在老订单上漏报。
- `remark` 来自外部文本，React Tooltip 默认文本渲染可避免 HTML 注入；不应使用 `dangerouslySetInnerHTML`。

## 已确认的实现决策

1. **赛果启动时机**：采用“计划开赛 + 120 分钟”后才自动批量查赛果。
2. **已取消的默认可见性**：默认“非停售”筛选不显示已取消；增加独立“已取消”筛选，在“不限/已取消”中可看浅灰 card。
3. **订单处理**：不改订单结算；仅当支付目标中存在已取消比赛时，在原支付确认之后增加一个是否仍然支付的确认弹窗。
4. **fixed-bonus 判定**：不改成“开赛后才请求”；它保留赛前赔率职责，通过有效 pool/赔率条件降低无效请求。

## Research 结论

- 仓库已使用官方批量赛果接口，请求过多的主要原因是错误的小 `pageSize`、找全候选后不提前结束、取消记录未识别导致重试，以及赛果从计划开赛时刻过早启动。
- 点击“刷新数据”还会另外引起按全部比赛 ID 的 fixed-bonus 请求；它不能被批量赛果直接代替，但可以先过滤没有任何有效 pool/odds 的远期 `Define` 比赛。
- 同一 fixed-bonus URL 重复主要来自多个快照轮次都全量补充、请求完成后不保留结果缓存，以及特定失败路径的前端官方兜底；不是批量赛果接口本身逐场请求。
- 2041458 现场不仅“列表缺失”，官方批量赛果和 fixed-bonus 都明确给出取消信号，应建模为独立 `cancelled` 终态，不是 `pending`、`stopped` 或伪赛果。
- `remark` 仅需扩展 JSON 比赛模型和转换/UI，无需迁移。
- 已取消比赛默认隐藏但可单独筛选；支付前额外确认只是风险提示，不会改变原订单结算规则。
- 本次整体属于新增状态、修正请求行为和新增展示的行为调整；如后续进入部署流程，按仓库规则应作为 minor 版本发布。
