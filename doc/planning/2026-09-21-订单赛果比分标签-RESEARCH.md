# 订单赛果比分标签 Research

## 需求边界

- 订单卡片和订单明细中的比分赛果 tag 不再显示“比分”前缀，普通比分只显示实际比分，例如 `0:1`。
- 赛果属于“胜其他 / 平其他 / 负其他”时，tag 需同时显示中文类别和具体全场比分，例如 `胜其他 6:0`。
- 本阶段只做 Research，不修改业务代码、订单数据或发布版本。

## 相关实现

- `app/FootballApp.tsx`
  - `matchResultOptionLabel` 根据订单比赛快照内的玩法选项查找赛果文案，查不到时直接返回 `optionId`。
  - 订单卡片和订单明细各有一处 `<Tag color="blue">比分 {scoreResult}</Tag>`，两处需保持同一展示口径。
  - `resultMatches` 只收集未完整判断，或虽标记失败但没有保存赛果的比赛；已有 `resultValues` 的历史订单不会自动重新进入赛果获取区。
- `app/data.ts`
  - 比分玩法的展示文案包含“胜其他 / 平其他 / 负其他”，对应内部 ID 是 `winOther / drawOther / loseOther`。
- `app/calculator.ts`
  - `winningOptionId("score", ...)` 先拼出具体比分；只有竞彩比分玩法明确列出的比分会返回具体比分 ID，其余按主胜、平局、主负分别返回 `winOther / drawOther / loseOther`。
- `app/sporttery.ts`
  - 投注赔率中的官方比分字段 `s1sh / s1sd / s1sa` 与内部 `winOther / drawOther / loseOther` 对应。
  - 赛果解析会同时产生 `values.score` 和 `fullScore`；前者是用于命中判定的玩法选项 ID，后者保留具体主客队进球数。
- `app/results.ts`
  - `judgeSlipWithResults` 把 `MatchResult.values` 写入订单 `resultValues`，但没有把 `MatchResult.fullScore` 写入订单。
- `app/order-model.ts`
  - 云端 `CompactOrder` 只保存已选玩法和已选选项，不保存完整比赛市场，也不保存 `MatchItem.result`。
  - `resultValues` 可经本地与云端订单互转持久化，但目前没有用于保存具体全场比分的字段。
- `app/server/orders-service.ts` 与 `drizzle/0000_white_iron_lad.sql`
  - 订单主数据保存在 `user_orders.data_json`；增加可选的订单 JSON 字段不需要 D1 表迁移，但要同步类型、验证、转换和更新链路。

## `winOther` 的来源与截图根因

`winOther` 是项目内部的比分玩法选项 ID，不是应直接显示给用户的文案。它有两条来源：

1. 投注选项侧：官方 CRS 赔率字段 `s1sh` 映射为内部 `winOther`，选项文案是“胜其他”。
2. 赛果判定侧：如果具体比分是主胜，但不在竞彩单列的 12 个主胜比分中，`winningOptionId` 返回 `winOther`；例如 `6:0`、`6:1`、`7:2`。平局和主负同理归入 `drawOther` 或 `loseOther`。

截图中显示 `winOther` 的直接原因是：

- 订单压缩快照只含用户已选的玩法和选项。该场如果没有投注“胜其他”，快照中就找不到 ID 为 `winOther` 的选项及其“胜其他”文案。
- `matchResultOptionLabel` 查找失败后以原始 ID 兜底，因此展示了 `winOther`。
- 普通比分 ID 本身就是 `0:1` 这样的可读文字，所以同样的兜底逻辑在普通比分上看起来正常，只在三个“其他” ID 上暴露。

## 数据缺口

- 比分接口和批量赛果解析都已经取得真实 `fullScore`，不需要新的上游接口。
- `values.score` 不能直接改成始终保存真实比分。它现在是玩法命中 ID；若将“胜其他”的 `winOther` 改成 `6:0`，现有 `hits` 与已选选项 ID 比较会失去命中，影响订单成功状态和奖金计算。
- 因此需要同时保留两种语义：
  - `resultValues.score = "winOther"` 用于正确命中“胜其他”；
  - 独立的具体全场比分，例如 `{ home: 6, away: 0 }`，用于展示和后续兼容。
- 现有历史订单如果只保存了 `winOther / drawOther / loseOther`，不可能从这一个类别 ID 反推唯一具体比分。

## 建议实现方向

- 将订单已判定比赛的具体全场比分作为独立、可选的按 `matchId` 映射持久化，不改变 `resultValues` 与 `hits` 的现有语义。
- `judgeSlipWithResults` 在保存玩法赛果时同步保存 `MatchResult.fullScore`；本地与云端订单转换、云端 JSON 验证和批量判定更新必须一起支持。
- 将比分 tag 文案收敛为一个不依赖“订单已选选项”的纯函数：
  - 普通比分：显示具体比分，不显示“比分”。
  - 三个“其他”：使用稳定的 ID 到中文文案映射，再追加已保存的具体比分。
  - 历史数据没有具体比分时，至少显示“胜其他 / 平其他 / 负其他”，不再泄露内部 ID。
- 新字段可随 `data_json` 保存，预计无需新增 D1 迁移；但这是订单数据格式的向后兼容扩展，需保证旧订单缺少该字段时仍能正常加载。

## 验证范围

- 纯函数测试：普通比分、`winOther / drawOther / loseOther` 有具体比分和无具体比分的展示文案。
- 赛果判定测试：具体比分归类为“其他”时，`resultValues.score` 仍为玩法选项 ID，同时持久化具体全场比分，命中、失败和奖金计算不变。
- 订单模型往返测试：新字段经 `SavedSlip <-> CompactOrder` 不丢失，历史订单没有新字段仍通过验证。
- 云端服务测试：批量判定写入 JSON，并保留现有并发冲突与整批成功/失败语义。
- 浏览器验证：订单卡片和订单明细两处，分别覆盖普通比分和三种“其他”；检查桌面端、移动端布局与控制台错误。
- 实施完成后按发布前要求运行 `npm test`、`npm run lint` 和 `npm run build`。

## 待确认问题

1. 无数据缺口的目标展示是否确认为：普通比分显示 `0:1`，“其他”显示 `胜其他 6:0` / `平其他 4:4` / `负其他 0:6`？
2. 历史订单中已经只保存 `winOther / drawOther / loseOther` 的记录无法从订单本身还原具体比分。是否接受“历史记录先只改为中文‘胜其他 / 平其他 / 负其他’，今后新获取或明确重新获取赛果的订单才追加具体比分”？如果要求历史记录也补齐，需要另外设计按比赛 ID 重新获取并回写的补数流程。
