# 订单瀑布流批次空白 Planning

关联 Research：`doc/planning/2026-10-08-order-masonry-batch-gap-RESEARCH.md`

## 实施方案

1. 将批次拆列工具改为对全部当前已加载订单按全局索引拆分左右列。
2. 移除订单列表的独立批次布局容器，保留每次加载 10 单的分页计数。
3. 卡片使用全局索引；桌面端向各列末尾追加，移动端按全局索引恢复自然顺序。
4. 桌面端分别观察两列末端以提前加载短列，移动端继续观察列表底部。
5. 增加布局纯函数测试，并验证桌面端追加稳定性与移动端顺序。

## 接口与兼容

- 不修改订单排序、筛选、API、D1、订单结构或持久化顺序。
- `ORDER_LIST_BATCH_SIZE` 继续控制每次增加的可见订单数量。
- 不需要数据库迁移或历史数据处理。

## 发布影响

- 这是订单列表布局问题修复，正式发布时按 patch 更新版本。

## 实施与验证结果

- 当前已加载订单共用一对左右列，仍按全局顺序分配为左 `[1,3,5...]`、右 `[2,4,6...]`；每次加载数量仍为 10。
- 桌面端分别观察左右列末端，短列进入 360px 预加载范围时即可增加下一批，不再等待高列底部。
- 高矮差测试中，第 12 单直接接在第 10 单下方，间距保持 16px；加载后原有订单列归属和位置保持稳定，浏览器控制台无 error。
- 390px 移动端加载前后视觉顺序分别为 1→10 和 1→20，所有卡片 `x=24`、宽度 `327px`，浏览器控制台无 error。
- `npm test`：187 项通过；`npm run lint`：0 errors，保留 3 条既有 `<img>` warning；`npm run build` 与 `npm run build:html` 通过。
