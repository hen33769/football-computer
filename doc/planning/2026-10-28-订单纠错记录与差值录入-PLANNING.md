# 订单纠错记录与差值录入 Planning

日期：2026-10-28。状态：实现与验证完成，纳入 v1.39.0 发布范围。

关联 Research：`doc/planning/2026-10-28-订单纠错记录与差值录入-RESEARCH.md`。

## 目标与验收口径

- 订单页保留累计支出、累计税后收入旁的纠错入口，改为弹窗新增一笔带正负号的差值，不再填写累计目标值。
- 每笔纠错包含收入／支出类型、非零差值、可空归属日期和可选备注；日期只允许今天及过去，备注最多 200 字。
- 无日期纠错计入初值；有日期纠错计入对应日收入或支出。旧收入／支出纠错值分别迁为对应类型的无日期初值。
- 记录只追加，不编辑或删除。记录旁提供“补差”，预选原类型和原日期，保存新的关联记录。
- 游客与云端使用相同语义；完整 JSON 备份 v6 支持导出、合并导入和覆盖恢复，重复导入不重复入账。
- 覆盖恢复归档原账本并激活备份账本；合并导入保留当前账本并按稳定来源 ID 去重。
- 统计汇总、趋势图、完整备份、前端状态与 D1 数据保持同一口径；所有金额在持久化和接口写入层使用整数分。

## 总体设计

### 领域模型

- `FinanceCorrectionKind = "expense" | "income"`；income 始终指税后收入，纠错不改变订单税额。
- `FinanceCorrectionEntry` 是不可变流水，核心字段为本地 ID、稳定来源 ID、类型、`deltaCents`、`effectiveDate`、备注、创建时间、来源、创建顺序上的纠错前后值、可选 `adjustsEntryId`。
- 创建时间用于审计和记录排序；归属日期用于趋势归集。空归属日期表示初值，两者不互相推导。
- 当前累计纠错仍缓存于 `user_finance_corrections`，作为读取汇总；流水是审计来源。每次写入和导入后校验汇总等于当前有效账本流水之和。
- `FinanceLedger` 表示一个账本代次。每个用户只有一个 active 代次，可以有多个 archived 代次；统计、趋势和普通导出只读取 active 代次。
- 稳定来源键采用 `(originId, originEntryId)`。本机新记录使用持久化 originId 和随机 entryId；导入后保留来源键，用于重复合并去重，本地数据库 ID 可重新生成。

### 金额与请求约定

- 表单继续以元显示，但输入使用 `InputNumber stringMode` 保存十进制字符串；统一工具严格解析为安全整数分，拒绝空值、零、超过两位小数、非有限值和超出安全整数范围的金额。
- 新增纠错 API 接收 `deltaCents`，不接收浮点元值；备份文件内所有财务金额也使用整数分。
- 汇总 `FinanceResponse` 暂时保留现有元值字段，减少订单页改动；流水接口返回整数分，由展示层格式化。
- 新增提交必须带 `requestId` 和 `expectedRevision`。同 requestId、同内容返回首次结果；同 requestId、不同内容返回 409。

### 统一个人数据版本

- 新增个人数据 `dataRevision`，范围限定为完整个人备份中的订单、应用设置和当前账本；球队标签、个人比赛备注和公共比赛不纳入该版本。
- 创建、更新、删除、批量变更订单，保存设置，新增纠错以及完整导入，都必须在各自写入事务中将 `dataRevision` 增加一次。
- 现有订单 `updatedAt`、设置 revision、财务 revision 继续承担各领域并发检查；`dataRevision` 用于完整导出一致性和导入预览后的全局冲突检查。
- 完整导出在读取前后核对同一 dataRevision；发生变化则重新读取一次，仍变化时返回 409，避免拼接不同时间的订单、设置和账本。

## 数据库迁移

新增 `drizzle/0013_finance_correction_ledger.sql`，同时更新 `db/schema.ts`；不改写旧迁移。

### 正式表

1. `user_personal_data_revisions`
   - `user_id` 主键、`revision`、`origin_id`、`updated_at`。
   - originId 对用户持久化且不从账号名或 user_id 派生，备份只暴露 originId。
2. `user_finance_ledgers`
   - `id`、`user_id`、`status(active/archived)`、`source`、`created_at`、`archived_at`、可选 `restore_operation_id`。
   - 建立用户 + 状态索引，并用部分唯一索引保证每个用户最多一个 active 账本。
3. `user_finance_correction_entries`
   - `id`、`user_id`、`ledger_id`、`origin_id`、`origin_entry_id`、`kind`、`delta_cents`、`effective_date`、`note`、`source`、`request_id`、`created_at`、可选 `source_created_at`、`correction_before_cents`、`correction_after_cents`、`revision_after`、可选 `adjusts_entry_id`。
   - 唯一键：同一账本内 `(ledger_id, origin_id, origin_entry_id)`；用户 + requestId 对普通写入唯一。索引覆盖用户／账本／创建时间／ID和账本／日期／类型。
4. 调整 `user_finance_corrections`
   - 增加 `active_ledger_id`；保留收入、支出累计值、revision 和 updated_at，作为当前账本汇总与并发入口。
5. `user_data_import_operations`
   - 保存用户、requestId、备份摘要、策略、预览 dataRevision、状态、结果摘要和时间，负责完整导入幂等与恢复。
6. 不可见导入暂存表
   - 至少包含订单暂存、纠错暂存和设置／元信息暂存，以 import operation ID 隔离；暂存数据不参与任何在线查询。
   - 最终提交用少量 `INSERT ... SELECT`、删除／更新和 ledger 激活语句完成原子切换，避免按记录逐条修改线上数据。

### 迁移与初始化

- 为现有用户建立个人 dataRevision 与稳定 originId；为已有 `user_finance_corrections` 建立 active 账本。
- 将非零旧支出、收入纠错分别写成 `legacy-migration` 无日期流水；差值保留正负，备注标识“升级前累计值，原始明细不可追溯”。旧 updated_at 仅存入来源时间，界面显示原时间未知，不冒充创建时间。
- 零纠错不生成流水；汇总金额、revision 和最终累计总额在迁移前后保持不变。
- 初始化函数必须可重复调用：新用户自动创建 revision、active ledger 和零汇总；并发首次访问不能产生两个 active ledger。
- 本地迁移使用同样的稳定来源键和幂等标识，重复启动不能重复生成旧余额。

## 服务端与 API

### 财务服务

- 在 `app/server/finance-service.ts` 拆分读取汇总、读取 active ledger、校验新增纠错、事务写入、分页记录、趋势聚合和旧 PATCH 兼容逻辑；金额继续复用 `app/server/money.ts`。
- 新增纠错事务顺序：识别 requestId 重试 → 校验 finance revision → 读取实时订单金额 → 校验调整后对应总额非负 → 插入流水 → 更新汇总和 revision → 增加 dataRevision。
- 用 D1 batch 内 guard 保证所有步骤整批成功或失败；不能以事务后的单条 `changes` 作为唯一冲突判断。使用真实 SQLite/D1 适配测试验证 guard 失败会回滚流水与汇总。
- `adjustsEntryId` 只允许指向当前用户、当前 active ledger、相同类型的记录；归属日期默认由前端带出但服务端不强制相等，因为跨日期补差是允许且需明确展示的行为。
- 全局收入或支出最终总额不得小于零；某一天或某一历史时点可以为负，不做截断。

### 财务接口

- `POST /api/finance/corrections`
  - 请求：`kind`、`deltaCents`、`effectiveDate | null`、`note`、`requestId`、`expectedRevision`、可选 `adjustsEntryId`。
  - 响应：更新后的 finance、创建的 entry 和 dataRevision。
- `GET /api/finance/corrections`
  - 支持 kind、active／指定 archived ledger、limit 和基于 `(createdAt,id)` 的游标；默认每页 20，服务端限制最大页长。
  - 返回 entries、nextCursor、当前 active ledger 信息和可读的归档账本列表。
- 保留现有 `PATCH /api/finance/corrections` 一个兼容周期：把绝对目标值转换为当前 active ledger 的无日期差值，最多产生收入和支出各一条 `legacy-client` 流水；强制 expectedRevision。重复绝对目标写入不生成零流水。
- `GET /api/finance` 增加 dataRevision／activeLedgerId（客户端只使用需要的字段）；现有订单金额与纠错汇总字段保持兼容。

### 个人版本写入改造

- 新增 `app/server/personal-data-revision-service.ts`，提供初始化、原子 guard 和 revision 增量语句。
- 调整 `orders-service.ts` 所有创建、更新、删除、支付、结账、撤回和批量操作：业务写入与 dataRevision 增量放在同一 batch，每个 API 请求只加一次；找不到订单的幂等删除不加版本。
- 调整 `settings-service.ts` 和新纠错事务，同样在成功业务写入后只加一次 dataRevision。
- API 响应携带最新 dataRevision；`FootballRoute` 在排队写入真正执行时读取最新 finance revision，避免在排队前捕获旧 revision，并在账号切换后丢弃旧账号结果。

## 趋势口径

- 扩展 `FinanceTrendDailyAmount/Point`，分别保留订单支出、支出纠错、订单税后收入、收入纠错和税额；同时输出合计字段，供图表与 tooltip 使用。
- 查询 active ledger：`effective_date IS NULL` 的收入／支出合计作为初值；有日期流水按 effective_date 和类型汇总，与订单日金额合并。禁止使用流水 created_at 归集。
- 日期范围开始前的订单和有日期纠错都预累加；范围后的事件不进入范围末点。无日期值永远只进入初值，不能再次作为日期事件计算。
- 当日收入 = 订单税后收入 + 收入纠错；当日支出 = 订单支出 + 支出纠错；利润按合计收入减合计支出。税额只来自订单。
- 只有初值而没有日期事件时，趋势弹窗显示初值摘要；如绘图需要锚点，仅用查询日或今天展示，不写回流水，也不宣称该日发生纠错。
- 更新趋势说明和 tooltip，明确订单金额、纠错、当日合计与累计值；筛选盈亏仍只统计筛选订单。

## 游客存储

- 新增 `app/guest-personal-store.ts`，以一个版本化快照作为游客订单、设置、财务账本和本地比赛的完整恢复边界；快照包含 revision、originId、active ledger、归档 ledger 和 correction entries。
- 首次读取时从现有订单／支出／收入／设置／比赛 key 幂等迁移。旧游客总额减当前订单口径得到收入和支出历史初值；保留旧总额，不制造日期或备注。
- 所有游客写入通过一个 `updateGuestSnapshot(expectedRevision, updater)` 完成，单次序列化后原子替换主 key；写入失败保持旧快照并向页面返回错误。
- 监听 storage 事件：其他标签页 revision 变化时刷新；提交旧 revision 时提示数据已更新，不覆盖较新的快照。
- 旧 key 在一个兼容版本内只读兜底，不再双写；确认新快照成功后标记已迁移，后续版本再移除兜底。

## 前端交互

### 纠错弹窗

- 新增 `app/components/FinanceCorrectionsModal.tsx`，包含“新增纠错”和“纠错记录”两个视图；云端和游客共用展示组件，只注入不同数据适配器。
- 累计支出、累计税后收入卡片保留编辑按钮，分别预选 expense／income 打开新增表单；统计标题旁增加“纠错记录”按钮，从历史视图打开。
- 表单字段：类型、差值、归属日期、备注。日期默认空，可清除，禁选明天及以后；备注显示字数；金额不预填。
- 预览同时展示当前总额、此次正负差值、调整后总额和累计纠错前后值；无日期显示“计入初值”，有日期显示具体归属日。保存期间禁止重复提交，失败保留草稿。
- 记录桌面端用表格、移动端用卡片；显示创建时间、归属日期／初值、类型、差值、累计前后、备注、来源和补差关联。支持类型筛选、翻页、active／归档账本切换。
- “补差”打开新增视图并带出原类型、原归属日期和关联 ID，金额留空；提交前再次展示归属含义。原记录不改变。
- 卡片副行统一写“累计纠错 ±¥X”；游客也展示订单金额与纠错拆分，消除原来游客直接修改累计总额的特殊语义。

### 客户端状态

- 在 `app/api-client/finance.ts` 增加流水类型、分页查询和 POST；在 `app/cloud.ts`／`FootballRoute.tsx` 增加 finance revision、dataRevision、active ledger 和新增纠错回调。
- 云端成功后以服务端 finance 为准刷新汇总；409 时刷新 finance 和记录，让用户重新核对预览，不自动改写差值后重试。
- 游客成功后从新快照推导订单金额、纠错和总额；不再单独 setExpenseTotal／setIncomeTotal 持久化绝对值。
- 关闭弹窗或切换账号时取消或忽略旧分页请求；归档记录只读，不能从归档账本发起补差。

## 完整备份 v6

### 文件模型与校验

- 新增 `app/data-backup.ts` 定义 v6 schema、严格解析、规范化、摘要和 v5 兼容转换。拒绝未知 kind、非法金额／日期／备注、重复稳定 ID、断裂或跨类型补差关系和汇总不一致。
- full v6 包含 `originId`、导出时间、个人 dataRevision、orders、settings、active finance ledger／entries／校验汇总和 matches 快照。默认不导出目标端归档账本。
- 文件不包含 user_id、登录信息、服务端 revision 或权限；来源创建时间作为审计信息，导入时间由目标端另记。
- 单独 orders／settings／matches 的文件保持原范围；只有 full 处理财务账本。

### 云端导出

- 新增 `GET /api/users/me/backup`，服务端读取全部个人订单、设置和 active ledger，不依赖页面当前分页；用 dataRevision 前后校验保证一致快照。
- 公共比赛不是个人事务的一部分，文件记录独立的比赛快照版本。恢复时沿用现有权限，并在预览／结果中与个人数据分开显示，不能把两者描述为一个原子事务。
- 客户端收到完整 v6 后再下载，不使用当前页面 `savedSlips` 拼装云端完整备份。

### 导入预览与提交

- 新增 `POST /api/users/me/backup/import/preview`：严格解析 v5／v6，返回备份摘要、策略下的新增／更新／删除／跳过／冲突数量、初值选择、预计汇总、expectedDataRevision、公共比赛影响和文件摘要。
- 新增 `POST /api/users/me/backup/import`：携带 requestId、策略、expectedDataRevision、初值选择和原文件；服务端重新解析并核对摘要，不信任预览的计算结果。
- 提交先写 `user_data_import_operations` 和不可见暂存表；暂存完成后再次核对 dataRevision，在一个最终 D1 batch 内应用个人订单、设置、账本和 revision，并标记 operation 完成。失败时线上数据不变，暂存可重试或清理。
- 相同 requestId + 摘要 + 策略返回首次结果；内容或策略变化返回 409。设置暂存和过期清理路径，不让失败导入永久占用空间。
- 实现前用本地 D1 与实际约束验证请求体、绑定变量、单行和 batch 上限，据此设置明确的文件大小、订单数和流水数上限；超限在预览阶段返回 413，不进入暂存。

### 合并规则

- 订单沿用 ID 合并语义，设置沿用现有 `unionAppSettings`；财务流水在当前 active ledger 内按 `(originId,originEntryId)` 去重。
- 同稳定 ID 内容相同则跳过，内容不同则整批冲突；补差引用按导入映射重连，关联目标缺失或类型不同则拒绝。
- 升级后每条无日期流水和有日期流水同样正常合并。只有 `legacy-migration` 的不可拆分历史余额进入“历史初值策略”。
- 历史初值默认保留当前；预览允许选择使用备份初值，以一笔有稳定来源键的无日期调整实现目标差额，不删除当前历史。重复导入保持幂等。
- v5 合并只合并订单、设置等既有内容，不叠加文件总额；预览明确提示无纠错明细。

### 覆盖规则

- 个人订单、设置和账本按文件恢复；恢复前校验文件订单口径 + 纠错等于文件汇总。
- 当前 active ledger 改为 archived，新建 ledger 装载备份流水后激活；汇总根据新 ledger 重算，不能直接信任文件总额。恢复事件记录来源摘要和数量。
- v5 覆盖用文件总额减文件订单合计生成收入／支出无日期 `legacy-backup` 初值，不虚构日期和旧备注。
- 默认记录、趋势和后续导出只读新 active ledger；历史弹窗可切换查看归档账本。
- 公共比赛按独立权限和结果处理；个人恢复成功、比赛恢复失败时必须分别报告，不显示“全部原子恢复成功”。游客的比赛属于同一本地快照，可以随完整覆盖一起原子切换。

### 导入 UI

- 完整导入读取文件后先打开预览弹窗，不直接执行；显示个人数据变化、财务新增／跳过／冲突、初值策略、覆盖归档说明、预计收入／支出和公共比赛影响。
- 覆盖确认文案明确“当前账本将归档并可只读查看”；合并确认文案明确“重复纠错不会再次累计”。有冲突或校验错误时禁用提交。
- 导入成功后一次性刷新订单、设置、finance、纠错记录和客户端 revision；分别报告个人数据与公共比赛结果。

## 兼容策略

- 数据库只新增迁移。旧汇总表继续服务现有读取，但写入统一经过流水服务。
- 旧 PATCH 保留一个版本并强制 revision；新页面只用 POST。后续确认无旧客户端后再单独移除。
- v5 完整文件继续可导入；v6 文件由旧版本拒绝属于预期，不做降级写出。
- 游客旧 key 保留一版只读迁移兜底；导出 v6 前必须已完成新快照迁移。
