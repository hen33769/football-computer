# 订单确认 Research

## 需求结论

- 订单新增持久化确认状态。采用 `confirmedAt?: string` 保存确认时间，缺失表示未确认；历史订单默认未确认。
- 只有同时满足“已结账、订单状态为成功、尚未确认”的订单可以执行确认。
- 订单卡片的确认按钮放在撤回按钮左侧；确认后保留“已确认”状态展示，不能重复确认。
- 订单进度筛选新增“未确认”，精确定义为“已结账、成功且 `confirmedAt` 为空”。
- 撤回结账会清除确认状态；再次判断已结账订单或修改已确认订单的税额会清除确认状态，因为最终结果或税后金额已改变。

## 现有实现与影响范围

- `app/types.ts` 与 `app/order-model.ts` 分别维护页面订单和云端紧凑订单；所有订单写入最终经过 `app/server/orders-service.ts`。
- 云端订单列表的进度筛选由 `OrderProgressFilter`、`app/api/orders/route.ts` 与 `ordersWhereClause` 串联；游客模式在 `FootballApp.tsx` 内执行同口径筛选。
- 页面订单操作通过 `OrderSyncIntent.operation` 调用 `/api/orders/bulk`，服务端已有版本冲突检查和 D1 `batch` 整批事务语义，适合新增 `confirm` 操作。
- `user_orders` 为列表查询保存独立的进度与状态列。新增 `confirmed_at` 列可让“未确认”筛选直接使用索引字段，避免依赖 JSON 查询。
- 撤回结账当前保留税额，但会清除 `settledAt` 和 `settledPrize`；确认状态需要同时清除。

## 约束与风险

- 服务端必须重新读取当前订单并校验已结账、成功、未确认，不能信任客户端提交的 `confirmedAt`。
- 普通更新不能让客户端伪造首次确认；确认只能通过 `confirm` 操作写入。普通编辑允许保留已有确认时间，但税额变化时清除确认。
- 已确认订单若重新判断赛果，确认状态应失效，避免“已确认”对应旧赛果或旧税额。
- 新迁移只增加可空列；历史订单无需回填，符合条件的历史已结账成功订单自然进入“未确认”筛选。

## 验证重点

- 服务端确认成功、重复确认、未结账、失败订单、其他账号、旧版本冲突与批量回滚。
- 云端 SQL 与游客筛选对“未确认”的定义一致。
- 模型往返、D1 列和 JSON 一致；撤回、赛果重判、税额编辑正确清除确认。
- 桌面端与移动端检查确认按钮在撤回左侧、确认后状态、筛选结果和控制台错误。
