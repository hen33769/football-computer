# 投注页比赛备注编辑 Research

日期：2026-10-13。Research 已完成并确认；实现与验收于 2026-10-15 完成，实施记录见对应 Planning。

## 已确认需求

- 个人备注属于账号，仅本人可编辑；与官方 `remark` 完全独立，不覆盖、不回退到官方备注。
- 官方备注仅在有值时显示 icon；个人备注 icon 固定显示，有值蓝色、无值灰色。两者放在比赛时间左侧，建议顺序为“官方 icon（有值时）→ 个人 icon → 时间”，个人 icon 紧挨时间。
- hover/focus 显示对应备注，个人 icon 点击打开编辑 Popover；旧数据无个人备注时默认 `''`。
- 使用独立接口修改指定比赛 ID 的个人备注；比赛信息更新后个人备注仍保留。
- 已确认将订单“明细”的个人备注查看/编辑纳入需求，不增加每场比赛时间；备注 icon 放在现有比赛标题区域。已支付、已结账、比赛过期均可操作本人备注，不改变订单投注与赛果。
- 未登录固定显示灰色个人 icon，点击提示登录，不保存游客备注。个人备注不随公共比赛缓存清理而删除，以支持历史明细入口。

## 追加调研：账号与缓存边界

- `app/cloud-server.ts` 的 `requireAuthenticatedCloudAccount(request)` 从会话获得账号；个人接口应直接复用，不接受客户端提供的 userId，普通用户与管理员都只能操作自己名下备注。
- `app/FootballRoute.tsx` 的 bootstrap 在确认登录后并行加载个人订单/财务/设置，可加入个人备注读取；`FootballApp` 以 accountId 为 key 重建，可传入当前账号的独立备注映射和保存回调。
- `clearCloudPersonalStorage` 当前不会清除 `CLOUD_STORAGE_KEYS.matches`。把个人备注写进现有公共比赛缓存会造成账号切换或登出后仍可见，需要避免。
- `app/cloud.ts` 的 `clearMatchSelections` 使用对象展开保留其它字段；`saveCachedMatches`、公共快照 POST 和订单快照也会带上扩展字段。单纯给 MatchItem 增加个人字段存在意外上传到共享比赛表的风险。
- `app/FootballApp.tsx` 的 `exportData` 直接导出比赛缓存、订单快照；导入也使用完整 MatchItem。个人备注建议不嵌入这些对象，本次不改变导入导出格式。
- `app/server/settings-service.ts` 已有 revision 条件 UPDATE 和 409 冲突模式，可参考但需要适配备注首次创建与空值记录。
- `tests/helpers/sqlite-d1.ts` 当前仅加载部分历史迁移；新增个人备注服务测试需显式加载新迁移，避免只测 JS 而未验证真实 SQL。

## 推荐设计（待 Planning 细化）

### 独立存储与读取

新增 `user_match_notes` 表：`user_id`、标准化 `match_id` 组成主键，`note TEXT NOT NULL DEFAULT ''`、`revision INTEGER NOT NULL DEFAULT 0`、`updated_at`。userId 外键指向 users，删除账号时级联删除；不关联共享比赛表的删除生命周期，避免比赛缓存清理时误删个人备注。新增迁移，不改旧迁移。

推荐用独立的 `PersonalMatchNote` / `Record<matchId, noteState>` 表示备注，不扩展公共 MatchItem；MatchCard 按标准化 ID 接收 `personalNote ?? ''`。这样“随 card 保存”表示该场比赛的备注独立持久化，UI 随卡片展示，而非回写整张比赛 JSON。缺字段、缺行都解释为空，不回填历史比赛或订单。

建议只读取当前页面比赛 ID 对应的备注，批量读取，不为每个 card 单独请求。初始化、刷新后新增比赛、载入/复制仍含可售比赛的订单，以及打开历史订单明细时补读；同账号同场比赛复用一份备注，无关筛选和排序。返回不存在的行应明确映射为空和 revision 0；读取失败要区分“未加载”与“空备注”，提示重试，不能把失败当空值并允许覆盖。

### 独立接口建议

- `GET /api/users/me/match-notes?ids=...`：鉴权后批量查询当前账号备注，限制数量、归一化及去重 ID；响应 `Cache-Control: private, no-store`，不配置公共跨域读取。
- `PATCH /api/users/me/match-notes/[matchId]`：请求 `{ note, expectedRevision }`，响应 `{ matchId, note, revision, updatedAt }`；只接受备注字段，不写 shared_matches、赔率、赛果或订单。
- 未登录返回 401；非法 ID/字段/长度返回 400；同账号同场版本不匹配返回 409。其他账号即使有同一比赛 ID，也只会更新调用者自己的行，无“代替别人修改”的入口。
- 不建议要求比赛仍存在于 shared_matches：历史订单比赛可能已清理。验证规范 ID 后可创建个人备注，不创建共享比赛数据。ID 格式校验应兼容仓库现有官方/手工比赛 ID，Planning 时检查 `app/data.ts`、手动订单入口的 ID 规则。
- 首次保存用唯一主键与条件 INSERT/UPSERT 原子处理；后续用 revision 条件更新。清空时保留空行并递增 revision，避免删除后版本回到 0 导致陈旧编辑被错误接受；不采用先 SELECT 再无条件 UPDATE。

### 刷新与账号隔离

个人备注映射独立于比赛对象，官方刷新、官方兜底、快照保存、赔率更新和赛果更新不操作它。因此无须为本功能重构现有共享比赛 JSON 的并发写入。

保存成功按返回 matchId 更新备注映射，不用返回旧整卡替换当前比赛；仍需防止“保存后较早发出的 GET 返回旧值”覆盖新备注，可比较 revision 并校验请求所属账号/请求代次。切换账号、登出时清空备注映射与草稿，取消/忽略旧账号未完成请求；异步响应不得落到新账号状态。

建议本次不做持久化浏览器个人备注缓存，登录后从专用接口读取；这样沿用现有公共比赛缓存不会泄露私人内容。若后续需要离线缓存，另加按账号命名空间的私有缓存与登出清理，不使用现有 matches key。公共比赛服务保存也可显式剔除已知个人字段作为边界防护，不能仅清除选中项就认定数据为公共。

### UI 与交互建议

- 官方 icon 保持只读，Tooltip 标注“官方备注”；个人 icon 使用区别明确的编辑/便签图标，Tooltip 标注“个人备注”，空值提示“暂无个人备注，点击编辑”。避免两个 InfoCircle 难以辨认。
- 个人有值蓝色、空值灰色，同时用 aria-label 和文本区分状态；保留键盘操作，手机扩大点击区域，限制浮层宽度和长文本换行。
- Popover 显示多行文本框、保存与取消。推荐保存按钮立即提交；点击外部/取消丢弃未保存草稿，保存失败保留草稿，保存中禁用重复提交，Popover 打开时关闭个人 Tooltip。
- 推荐上限 2000 字符、保留内部换行、去除首尾空白；全空白保存为空，icon 变灰。按纯文本渲染，不解析 HTML。未改变内容时禁用保存，减少请求与版本冲突。
- 409 时保持本地草稿并提示重新读取当前版本，不自动覆盖服务器值；同一页面同场比赛打开编辑器期间的刷新不重置草稿。
- 个人备注无需自动改写已保存订单；投注页与历史订单明细按账号 + matchId 展示同一份当前个人备注。

## 已确认边界与交互建议

核心数据方向与历史入口均已确认：

1. 未登录/本地游客：已确认固定显示灰色个人 icon，点击提示登录，不保存游客个人备注。独立 HTML 入口也应给出同样可理解的入口反馈。
2. 备注保留：不随比赛 7 天缓存清理删除，通过订单明细提供历史查看/编辑入口，已获用户确认。

以下为可直接采用的交互建议：顺序“官方→个人→时间”、Popover 点击保存才提交、2000 字符限制、导入导出本次不包含个人备注。如需导出备份私人备注，应另设账号私有数据格式与显式导入策略，不能混入公共比赛快照。

## 历史订单入口核对与前文更正（2026-10-13）

- 订单卡片“明细”打开 orderDetail Drawer，使用订单内嵌比赛快照，不要求比赛仍存在公共缓存；已支付/已结账订单也可查看。“展开比赛选项”也能查看保存的选项。
- “载入投注”仅对未支付、未结账订单显示。loadSlip 调用 selectAvailableOrderBets，按当前比赛集合匹配并过滤不可售或赔率无效的选项；没有可用选项时提示“该订单没有当前可用的投注项”，不跳转投注页。成功后保存更新原订单。
- “复制投注”对已支付/已结账订单也显示，但同样过滤不可售选项；完全过期订单不能复制到投注页。成功后保存创建新订单。
- 依据：app/FootballApp.tsx 的 loadSlip、copySlip、订单卡片 actions、orderDetail Drawer；app/sporttery.ts 的 selectAvailableOrderBets。
- 更正前文“历史订单载入后可查看/编辑备注”的建议：只有仍含可售选项的订单满足此条件。补读备注与浏览器验证中的历史载入情景应以此限制为准。保留备注并不自动提供历史查看入口。
- 已确认优化：订单“明细”不增加每场比赛时间；在现有比赛标题区域显示官方备注（有值时）与个人备注 icon，复用私有 API 和 Popover；无需解锁订单或撤回支付，不改变历史投注内容。时间左侧的布局要求仅适用于投注页。
- 本轮演示为依据现有代码制作的交互示意，使用示例数据，不访问或修改真实订单。
