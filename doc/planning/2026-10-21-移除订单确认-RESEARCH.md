# 移除订单确认 Research

## 现有实现

- 订单确认由 `SavedSlip.confirmedAt` / `CompactOrder.confirmedAt` 表示，云端同时写入 `user_orders.confirmed_at` 和 `data_json`。
- `/api/orders/bulk` 接受 `operation: "confirm"`，服务端只允许已结账成功订单确认，并由服务端生成确认时间。
- 订单卡片为已结账成功订单展示“确认/已确认”，前端另有确认中的 loading 状态和成功通知。
- 订单进度包含 `unconfirmed`；游客端按订单数据过滤，云端按 `settled_at`、`status` 和 `confirmed_at` 查询。
- 撤回结账、重新判断赛果和修改税额会清除确认状态，因此确认逻辑还散布在订单模型、赛果处理、编辑、结账与撤回路径中。

## 影响范围

- 前端：`app/FootballApp.tsx`、`app/results.ts`、`app/cloud.ts`、`app/types.ts`。
- 共享模型与 API：`app/order-model.ts`、`app/api/orders/bulk/route.ts`。
- 服务端持久化与查询：`app/server/orders-service.ts`。
- 数据库与测试：`db/schema.ts`、`drizzle/0012_order_confirmation.sql`、`tests/orders-service.test.ts`、`tests/helpers/sqlite-d1.ts`。

## 兼容与约束

- `0012_order_confirmation.sql` 已属于发布历史，不能改写或删除；数据库现有 `confirmed_at` 列和索引继续保留，不做破坏性迁移。
- 当前应用不再读取、写入或返回确认状态。旧订单 JSON 中的 `confirmedAt` 在模型标准化或本地订单加载时丢弃，后续正常写入会自然清理 JSON 内的旧字段；数据库独立列中的历史值暂时保留。
- 旧客户端提交 `operation: "confirm"` 将由批量 API 作为无效操作拒绝；`progress=unconfirmed` 将被当作无进度筛选，保持现有非法查询值的兼容行为。
- 联赛命中率中的“未确认”表示比赛玩法尚无赛果，与订单确认功能无关，不在本次移除范围。

## 风险

- 若只移除页面按钮，旧客户端仍可调用确认接口，因此必须同步移除 API operation 和服务端分支。
- 若只移除筛选下拉，旧 URL 仍可能触发云端过滤，因此必须同步移除共享筛选值和 SQL 条件。
- 历史订单可能仍携带 `confirmedAt`；需要显式兼容清理，避免它通过对象展开继续出现在导出或接口响应中。
