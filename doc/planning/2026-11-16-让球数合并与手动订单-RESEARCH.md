# 让球数合并与手动订单 Research

## 现象与证据

- 用户截图为 2026-11-14 周六007 挪威 VS 威尔士（比赛 ID 2042757）。此前只读查询生产 `shared_matches`：该场 `rqspf.handicap` 缺失，主胜赔率 2.55、平 3.95、主负 2.03 存在。
- 此前只读请求体彩 `getFixedBonusV1`：该场让球赛果和让球赔率历史均含 `goalLine=-2`；历史中 09:40:59 主胜为 2.55，18:27:33 主胜为 2.44。截图赔率是早期有效赔率，不等于最新赔率。
- `app/FootballApp.tsx` 手动投注项标题对 `market.handicap ?? 0` 展示为 0，即使数据实际缺失；`app/manual-order-format.ts` 对缺失让球数不填括号，最终手动保存检查会拒绝缺失让球数。弹窗 0 并非此例真实缓存值。

## 数据流与缺口

- `app/sporttery.ts` 中 `convertSportteryMatches` 从 `hhad.goalLine` 转数值，缺失时写 `undefined`，实际字符串 `0` 保留为数值 0；现有测试明确区分二者。
- `mergeSportteryMatchCache` 与 `replaceSportteryMatches` 调用 `mergeSportteryMatchOdds`：按现有 `sameMatch` 找旧比赛，逐选项保留历史有效赔率，但直接采用新 market 的 handicap，缺失或 0 会丢失旧盘口。服务端 D1 刷新与前端缓存均复用此链路。官方非零新值也应覆盖旧值。
- `convertSportteryMorningMatches` 先用 fixed-bonus 最后一条历史替换 `hhad`；calculator 分支的 `enrichSportteryMatchOddsHistory` 只补赔率历史，不补盘口。常规模式列表与 calculator 同场合并时，后者一旦有任何赔率就整场覆盖前者，可能丢掉列表已有盘口。具体截图中哪次刷新丢失无法从当前单条状态还原。
- `mergeImportedMatch` 是导入合并的独立路径，新字段覆盖旧字段；`refreshSelectedOdds` 是订单显式更新赔率的独立路径。赛果有单独来源与快照；不能未经确认整体更改订单、导入或赛果合并语义。
- 手动订单按 matchId 查询时 `mergeSportteryFixedBonusMatch` 已从官方结果或历史读取盘口；手动选择来源是缓存时不会因打开弹窗自动补查。重新打开选择器只恢复文本中选项及赔率，不恢复手填盘口。

## 建议方案与风险

1. 针对自动比赛快照同 ID 合并：新盘口是有限非零值时采用新值；新值缺失、非有限或为 0 时，若旧值为有限非零则保留旧值；无可用旧值则保留缺失状态。严格使用标准化比赛 ID，避免跨比赛借用。
2. 已有测试明确允许官方真实 `0`，上述规则会在旧值非零时忽略真实归零，是用户要求的业务取舍；无法仅凭数值判断 0 是真实值还是占位值。盘口和赔率可能不同步或跨盘口变更，旧值仅为兜底，不保证最新，错误盘口会影响让球赛果及订单计算。
3. 修复官方快照内部合并和 fixed-bonus 盘口提取：可信官方非零盘口优先于缺失/0，再回退缓存。应检查同场 calculator 和列表合并，避免拿到详情却丢弃已有盘口；不扩大官方请求频率。
4. 手动选择弹窗缺失盘口展示“待获取盘口”，不再伪装为 0；选中后保留手工填写校验及重开时的手填值。若允许用户手动填错，仍需由用户核对。
5. 合并保护不能恢复已经丢失的旧值。截图比赛可由现有按 ID 查询官方 fixed-bonus 的路径得到 -2，但是否以及何时对已保存的公共缓存补齐，需单独设计；禁止自动批量改写生产数据。若官方接口失败或历史不可用，应继续明确显示缺失、允许手填。
6. 不需数据库结构迁移；需测试缺失/0/有效新值、无旧值、不同 ID、真实零的业务取舍、fixed-bonus 与列表/calculator 合并、弹窗显示及手工输入往返，并验证桌面与移动交互。测试应覆盖成功和接口失败，确保不改写已保存订单与赛果。

## 开发者确认

- 让球胜平负的 0 按无有效盘口处理；普通胜平负由独立玩法表示。按上述范围开始修复。
