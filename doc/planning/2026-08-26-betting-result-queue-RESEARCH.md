# 投注页赛果请求队列与重试 Research

## 需求边界

- 投注页自动获取已结束比赛赛果时，降低官方接口短时间请求密度。
- 每场比赛串行处理；请求失败的比赛重新放到当前队列末尾。
- 每场比赛最多重试 3 次（按“重试”语义解释为初次请求之外再尝试 3 次）。
- 当前正在请求的比赛卡片用加载图标替换 `VS`，其它未轮到的比赛不显示为正在请求。

## 现有实现

- `app/FootballApp.tsx` 的投注页 effect 会收集所有已展开日期中“已停售且没有完整赛果”的比赛。
- 原流程虽按比赛顺序 `await`，但一次 effect 会连续处理全部候选；每场 `requestMatchResult` 同时调用比分接口和 fixed bonus 接口。
- `bettingResultFetchingMatchIds` 当前一次性写入全部候选，只用于顶部数量标签，`MatchCard` 没有消费该状态，因此比赛中间始终显示 `VS`。
- 之前增加的 `autoResultRetryAtRef` 只记录下一次允许时间，没有失败次数和队列；失败/未结束项会由 `saleClock` 触发后再次进入候选。
- `MatchCard` 仅通过 `match.result?.fullScore` 判断显示比分；`{ home: 0, away: 0 }` 是对象，不会被 JSX 条件过滤。

## 风险与约束

- 失败可能是接口临时错误，也可能是比赛尚未结束；两者都需要重试，但未结束不应立即密集重试。
- 赛果请求与页面比赛刷新、赛事前瞻、手动 matchId 查询是不同流量；本次只调整投注页自动赛果队列。
- 不修改赛果解析、D1 结构或手动“获取赛果”按钮语义；成功结果仍按比赛 ID 批量写回云端。
- 队列必须按标准化 `matchId` 去重，并在页面离开投注页或进入临时订单时停止更新 UI。

## 拟定方案

- 使用单个串行队列，每个队列项携带 `match`、`retryCount` 和可选 `retryAt`。
- 初次请求失败或返回未结束时，若 `retryCount < 3`，增加次数并追加到队尾；未结束等待较长退避，接口错误等待较短退避。
- 每次请求前只把当前 `matchId` 放入 loading 状态，完成/失败后清除；卡片通过该状态以 `LoadingOutlined` 替换 `VS`。
- 同一场成功后从重试状态移除；达到 3 次重试仍失败则停止本次队列，保留下一次用户展开日期或后续刷新触发的机会。
- 保留不同比赛之间的最小请求间隔，避免串行队列仍形成连续突发。

## 待验证

- 失败项确实排到队尾，且每场不会超过 3 次重试。
- 同时展开多场比赛时只有当前队头显示加载图标。
- 全场/半场 `0:0` 仍可正常显示。
- 队列结束、离开页面、切换临时订单时不存在悬挂请求更新。
