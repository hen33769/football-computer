# 投注页赛果刷新、比赛取消与 remark 实施计划

> 状态：已实施并完成验证；未提交、推送或部署。

## 目标

- 保留 fixed-bonus 在赛前赔率、让球和单关信息上的职责，但不再对没有有效 pool/赔率的远期比赛全量请求。
- 投注页的自动赛果只在计划开赛 120 分钟后启动，正确使用批量接口上限、提前结束并识别取消终态。
- 对“曾经在完整官方列表中、当前开赛前已从完整列表消失”的比赛标记 `saleStatus="cancelled"`，并支持官方显式取消信号。
- 保存并显示官方 `remark`。
- 不改订单结算；支付目标含已取消比赛时，在原支付确认后增加一次风险确认。

## 已确认决策

1. 自动赛果起点为计划开赛时间 + 120 分钟。
2. `cancelled` 不纳入默认“非停售”，增加独立“已取消”筛选；“不限”中仍可见。
3. 不改订单结算、中奖计算或账本逻辑，只增加支付前额外确认。
4. fixed-bonus 不使用“是否开赛”作为请求门槛；它与批量赛果调度分开处理。

## 数据和接口设计

### 1. 比赛模型

- `MatchItem.saleStatus` 扩展为 `pending | selling | stopped | cancelled`。
- `SportteryMatch` 和 `MatchItem` 增加 `remark?: string`；转换时 `trim`，空白值不持久化。
- `MatchSaleState`、导入校验状态白名单、手动补单文案、可选性判定和日期可用性同步扩展。
- 状态优先级为：新的官方同场记录 > 明确 `cancelled` > 根据开赛时间计算的 `stopped/pending`。已取消比赛不得在原定开赛时间后被 30 秒时钟降级为 `stopped`。

### 2. 完整列表缺失推断

- `SportteryMatchSnapshot` 增加仅供合并使用的完整列表观测 ID 集（计划命名 `authoritativeMatchIds?: string[]`）。
- ID 集必须来自成功的原始 `getMatchListV1` 响应，在业务日过滤和 UI 隐藏过滤之前收集；calculator-only 兜底不提供该集。
- `mergeSportteryMatchCache()` 增加可选合并上下文。只有当旧比赛未出现在 incoming，也未出现在 `authoritativeMatchIds`，且当前时间早于计划开赛时间时，才标记 `cancelled` 并清理当前草稿选择。
- 官方列表失败、仅 calculator 成功时，继续使用现有保守的 `pending/stopped` 合并，不推断取消。
- 服务端官方刷新把观测 ID 集传入 D1 合并；前端直连官方兜底也使用同一合并规则。

### 3. 显式取消信号

- 增加 fixed-bonus `value.isCancel === 1` 解析；如该响应已被获取，则标记对应比赛 `cancelled`，不要求响应必须有赔率历史。
- 将批量赛果记录分类为 `completed | cancelled | unfinished`；`sectionsNo999` 中的明确“取消”标记为 `cancelled`，不生成伪比分或 `MatchResult`。
- 客户端批量赛果发现取消后，立即更新本地比赛并从 unresolved/retry 队列移除。
- 扩展现有按 ID 共享比赛更新：服务端只允许复制可信 `result`，或将已存在比赛设为 `cancelled` 并清选择；不接受客户端覆盖赔率、队名等其它元数据。

### 4. 兼容性与持久化

- `remark` 和 `cancelled` 都跟随 `shared_matches.data_json`，无需 D1 migration。
- 旧快照没有 `remark`、旧比赛只有三种销售状态时保持兼容。
- 不改写已保存订单的比赛快照，不回填其 `saleStatus`，不改结算。

## 风险与回退

- **最高风险：误判取消。** 以 `authoritativeMatchIds` 强制限定在完整 match-list 成功路径；决不使用 calculator 缺失推断。
- **赔率信息回归风险。** fixed-bonus 仅过滤所有 pool/odds 都无效的比赛，`OddsIn/Selling` 继续获取；手动查询不改。
- **客户端更新边界。** 取消持久化只能改现有 ID 的终态和选择，不得覆盖服务端比赛主体。
- **支付状态时效。** 第二次确认使用当前共享比赛集，不回写订单快照；它是风险提示，不承担取消结算规则。
- 无 D1 migration，回退代码后旧版会忽略 `remark`；但旧版不认识 `cancelled`，因此正式部署必须保持前后端同版发布。
