# 投注页批量赛果与逐场即时显示 Research

## 需求边界

- 投注页自动获取赛果改为优先调用官方按日期批量赛果接口，降低逐场访问频率；订单页的单场“获取赛果”继续保留现有方法。
- 批量请求的日期范围由候选比赛的实际开赛日期决定，每次最多覆盖 30 个自然日；超过 30 天拆分为多个请求。
- `pageSize` 根据请求日期范围内本地比赛列表数量设置（至少为 1）；如果服务端限制单页数量，则依据返回的 `pages`/`total` 继续顺序翻页，不能只取第一页。
- 批量响应中已匹配且可识别的比赛结果，收到后立即更新投注页比赛卡片，不等待其它日期区间或分页请求完成。
- 正在批量请求覆盖范围内、尚未处理完成的比赛显示加载 icon，替代 `VS`；成功、未结束或失败后清理对应比赛的加载状态。
- 保留现有失败/未结束重试、赛果解析、标准化比赛 ID 匹配和成功结果写回云端的语义。

## Research 现场验证

- 用户附图不是开发指令，而是接口请求被拦截时的 EdgeOne 567 页面证据。页面显示请求 ID `14693453485911730216`，时间为 `2026-09-02 10:45:30 UTC+8`。
- 直接请求用户指定的批量接口（`2026-08-31` 至 `2026-09-01`、`pageSize=30`）实际返回 HTTP 200、`success=true`、`value.total=22`、`value.pages=1`，并返回 22 条 `value.matchResult`。
- 同一批量接口将 `pageSize` 改为 1 时返回 `value.total=22`、`value.pages=22`、`value.pageSize=1`，证明接口支持分页。`resultCount` 在不同 pageSize 下表现不稳定，不能作为总条数或分页完成条件；应以 `total`、`pages`、实际新增 `matchId` 和空页共同校验。
- 批量记录包含 `matchId`、`matchDate`、`goalLine`、`sectionsNo1`、`sectionsNo999`、`matchResultStatus` 等字段。其中 `sectionsNo1` 是半场比分，`sectionsNo999` 是全场比分，`goalLine` 可直接作为让球值来源。
- 当前代码的订单页单场路径使用 `app/sporttery.ts` 中的 `getMatchScoreV1.qry`（以及让球接口），而附图 URL 是 `getMatchResultV1.qry`，后者目前也被赛事前瞻模块用作“比赛近况”数据源；两者不能混为同一个赛果解析入口。

## 现有数据流

### 投注页自动队列

- `app/FootballApp.tsx` 中 `activeView === "betting"` 的 effect 收集已停售且 `!hasCompleteMatchResult(match)` 的比赛。
- 当前队列在每次请求前根据 `AUTO_RESULT_REQUEST_INTERVAL_MS` 等待；当前间隔为 `2 * 1000` 毫秒。同一时间只处理一场比赛，比分和 fixed bonus 两个接口在该场内并行。本次目标是将投注页自动路径替换为“按日期批量请求”，而不是提高单场请求并发。
- `requestMatchResult` 成功后会立刻执行 `setMatchResults`，但投注页的 `MatchCard` 不读取 `matchResults`，而是读取 `match.result?.fullScore` 和 `match.result?.halfScore`。
- 自动队列成功后只把 `{ ...match, result: outcome.result }` 追加到局部 `resultUpdates`；整个 `while` 队列结束后才统一将 `resultUpdates` 合并到 `matchesRef.current`，再调用 `setMatches` 和 `saveCachedMatches`。
- 因此，接口已返回的结果虽然进入了 `matchResults`，但投注页比赛卡片依赖的 `matches[*].result` 在全部请求结束前仍未改变，造成用户看到比分整体延迟出现。

### 订单页手动批量获取

- 订单页“获取全部赛果”使用 `fetchAllMatchResults`，同样按比赛顺序等待，但 `requestMatchResult` 每场成功时直接写入 `matchResults`。
- 订单页赛果行的选择框读取 `matchResults[matchId]`，所以该路径本身已经可以逐场显示；批量请求期间按钮和手动选择控件仍被 `allResultsFetching` 禁用，这是独立的交互语义。
- 本次“投注页面”需求的直接阻塞点是投注页自动 effect 的 `matches` 批量更新，不应误改为并发请求或改变订单页手动操作。

### 批量接口与本地比赛模型

- `MatchItem.date` 是体彩业务日，`MatchItem.time` 由 `matchDate + matchTime` 组成，实际开赛日期应从完整的 `date/time` 解析，不能只按业务日分组。现有 `parseMatchDateTime` 已覆盖 `HH:mm` 和完整日期时间两种格式，建议将等价的纯函数下沉到可测试的公共模块，避免自动队列和批量请求各自解释日期。
- 批量接口按日期过滤，不接收比赛 ID 列表，因此一个日期范围可能返回当前页面之外的其它比赛。客户端应将响应暂存为 `Map<标准化 matchId, 批量记录>`，只把候选比赛 ID 映射回本地比赛，不能按列表位置或返回顺序写入。
- 批量记录的 `goalLine` 可用于构造带正确 `rqspf.handicap` 的临时 `MatchItem`，再复用现有比分结果计算逻辑。建议增加明确的批量记录适配器，而不是让通用单场 parser 猜测多个响应层级。

## 既有设计与约束

- `doc/planning/2026-08-26-betting-result-queue-PLANNING.md` 已确定：同一时间只请求一场、保留比赛之间的最小间隔、失败项重试/退避，且成功结果按比赛 ID 批量写回云端。
- `app/result-fetch-queue.ts` 只负责重试次数和退避时间，不需要新增队列状态或接口。
- `hasCompleteMatchResult` 要求全场和半场比分都存在；未完成或解析失败的结果不能提前写成比赛完整赛果。
- 比赛缓存通过 `saveCachedMatches` 保存时会清除投注选择，但保留 `result`；云端更新通过 `onCloudMatchesUpdate`，由 `FootballRoute` 调用 `updateMatches` 并按标准化比赛 ID 合并。
- 正式比赛数据和订单属于高风险数据；本次是展示时机调整，不涉及 D1 结构和远端迁移。
- 批量接口属于第三方外部依赖，返回字段、分页上限和防护策略可能变化；批量 parser 必须校验 `success`、`value`、数组和可识别比赛 ID，异常响应不能当成空赛果覆盖本地数据。

## 根因

现有自动队列把“结果已获取”和“结果应用到投注页比赛状态”分成了两个阶段：前者逐场完成，后者集中在队列结束后执行。间隔本身不是延迟来源，延迟来自 `resultUpdates` 的批量应用位置。改为批量接口后，如果仍等所有日期区间和分页结束再应用，仍会复现同类问题，所以批量响应的每一页/每个可识别结果都要先更新本地展示，再汇总云端写回。

## EdgeOne 567 拦截分析

截图中的 567 不是 CORS 报错，而是 EdgeOne 返回的自定义拦截响应。腾讯云官方状态码说明，567 可能来自 Web 防护自定义规则、速率限制或 Bot 管理规则；JavaScript challenge 也可能拦截无法处理挑战页面的 cURL/API 客户端。[EdgeOne 异常状态码参考](https://cloud.tencent.com/document/faq/1552/101095) 和 [EdgeOne 安全防护相关问题](https://cloud.tencent.com/document/product/1552/100604) 均说明了这一点。

从用户请求和截图能确认的是“请求在接口业务逻辑之前被边缘安全层拒绝”，不能仅凭 567 判断具体命中的规则。可能增加风险评分的信号包括：

- 同一 IP 在较短时间内连续访问单场接口；逐场自动轮询会把请求数量线性放大。
- 请求携带了手工拼接的浏览器 `sec-*`、`priority`、Origin/Referer 和 UA 组合，存在浏览器指纹、Origin 端口与实际运行端口不一致等异常特征。截图 URL 直接访问时也可能触发防盗链或 Bot 规则。
- `origin/referer` 只能影响站点配置的防盗链判断，不能证明请求被授权；cURL 也不会因为补齐这些头就获得浏览器挑战票据。
- 具体原因必须由站点所有者在 EdgeOne 安全事件中用请求 ID `14693453485911730216` 和时间 `2026-09-02 10:45:30 UTC+8` 查询确认。当前从本地实际请求看，去掉这些伪浏览器头并使用批量接口可以正常得到 JSON，但这只能说明拦截具有规则/时段/来源条件，不代表可以稳定绕过。

解决方向应以减少误报和请求量为主，而不是伪造更多请求头：

1. 投注页采用按日期批量接口，缓存本次批量响应并按 ID 分发，分页和日期区间之间保留间隔、避免重复请求。
2. 前端只发送必要的 `Accept: application/json`；不要依赖复制浏览器 DevTools 的 `sec-*` 头，也不要把 `localhost:3000` 当成通用授权凭据。
3. 若浏览器直连仍受跨域或 WAF 影响，使用自有服务端/受控边缘函数作为正常的数据代理、缓存和限频层；这不能绕过对方安全策略，代理出口仍可能被限制，且应遵守接口方的使用规则。
4. 如果能联系接口站点管理员，应提供请求 ID，请管理员针对合法调用方配置防护例外、合理速率或 API 鉴权，而不是在客户端反复重试。EdgeOne 的安全策略支持按 IP/请求条件配置防护例外，但这需要站点所有者权限。

## 推荐实现方向

1. 在 `app/sporttery.ts` 增加批量 URL 构造、批量 payload 校验和“批量记录 -> 现有 `ParsedSportteryMatchScore`/`MatchResult`”适配器；单场 `fetchSportteryMatchScore` 和订单页 `requestMatchResult` 保持不变。
2. 自动队列先按实际开赛日期生成不超过 30 天的日期区间；每个区间按本地比赛列表数量设置 `pageSize`，按 `pages` 顺序翻页，并在每次批量 HTTP 请求之间复用现有间隔。请求结果暂存于内存 Map，按标准化 `matchId` 取回候选比赛。
3. 每收到一页批量结果，就立即把其中可识别的完成结果合并到 `matchesRef.current`、`setMatches` 和本地缓存，同时追加到 `resultUpdates`；全部批量请求结束后仍一次性调用 `onCloudMatchesUpdate(resultUpdates)`，维持云端写入频率。
4. 批量请求开始时将该日期区间内仍待处理的候选 ID 放入 `bettingResultFetchingMatchIds`；某个 ID 已得到完整结果后立即移除，其余 ID 在分页/区间完成或进入重试队列时清理。现有 `MatchCard` 已支持 `resultLoading`，可复用加载 icon，不需要改成 `VS` 文案分支。
5. 批量响应没有某个 ID、只返回未完赛信息、解析失败或请求异常时，沿用现有未结束/错误退避和最多 3 次重试；不能把“响应中不存在”直接标记为无赛果。原单场方法继续作为订单页手动路径，并按确认后的策略决定是否作为自动批量失败的有限回退。

### 本地即时更新与云端批量写回

推荐只把“显示”和“本地缓存”提前，把云端写回继续批量化。这样满足结果逐场显示，同时保持此前已经确认的云端写入频率和结果集合语义。若队列中途离开页面，已成功的结果会留在本地缓存，但尚未结束的批量云端更新可能不会执行；下一次同步或刷新时仍需以云端数据为准，这是现有批量写回策略的自然边界。

如果改为每场成功后立即调用 `onCloudMatchesUpdate`，会增加 D1/API 写入次数，并使多个结果请求与云端写入交错，可能放大并发版本冲突；当前需求没有要求远端逐场持久化，不建议采用。

## 影响范围

- 预计修改 `app/sporttery.ts` 的批量接口 client/parser、`app/FootballApp.tsx` 的自动赛果 effect 和本地即时合并逻辑，可能抽取日期区间、分页和按比赛 ID 应用结果的纯函数。
- 预计新增或调整测试覆盖：批量 URL 参数、30 天切分、分页直到 `pages` 完成、重复/无关比赛过滤、`goalLine` 让球解析、批量记录转换、收到一页后立即显示、失败/未结束重试、加载 ID 清理，以及多个结果按 ID 合并且不覆盖其它比赛字段。
- 不新增 API、数据库字段、迁移、订单结构或结果解析规则。

## 验证计划（待 Planning 确认后执行）

- 单元测试验证逐场更新函数只修改匹配比赛的 `result`，保留其它比赛和投注字段。
- 保留并运行现有赛果队列/重试测试，再运行 `npm test`、`npm run lint`、`npm run build`。
- 浏览器验证投注页：第一场结果返回时卡片先出现比分，后续比赛继续显示请求间隔和加载状态，队列结束后所有成功结果仍在；检查控制台无错误。
- 浏览器验证投注页：批量请求期间候选卡片的 `VS` 变为加载 icon；收到任一批量分页后该场先出现比分，剩余比赛继续加载；日期区间超过 30 天时确认分段和分页均正常，检查控制台无错误。
- 使用 mock fetch 覆盖成功、分页、未完成、缺 ID、567/非 JSON 和服务端限制 pageSize 场景；不通过并发请求规避间隔。

## 待确认问题

- 推荐采用“投注页自动获取 batch-first；按实际开赛日期分段、按接口分页；结果按 ID 临时缓存并逐页即时显示；订单页单场继续走原方法；云端仍批量写回”的范围，请确认。
- 批量接口请求成功但某场没有返回记录或无法解析时，建议只进入现有退避重试，不立即对所有缺失场次切回单场接口，以免批量异常时又放大请求量；如果你希望自动回退单场接口，请确认回退时机（仅批量 HTTP/JSON 失败，还是单场记录缺失也回退）。
- 加载 icon 建议覆盖当前日期区间内仍待处理的候选比赛；某场在批量响应中成功后立即恢复比分，未返回/未完成的比赛继续显示加载直到本轮结束或进入重试。若你希望只给当前分页的比赛显示加载，请确认。
- 用户没有要求订单页“获取全部赛果”改变为批量接口或在批量期间允许编辑，因此本 Research 暂不扩大该范围。
