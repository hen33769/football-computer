# 订单未支付与差关筛选 Planning

日期：2026-08-31

关联 Research：`doc/planning/2026-08-31-order-payment-missed-filter-RESEARCH.md`

## 目标

- 在订单进度筛选中增加“未支付”。
- 增加“错失”多选筛选，选项为差1关至差8关，按订单中某个串关距离全部确认命中还差的场次数筛选。
- 保证游客本地筛选与账号云端 D1 筛选使用同一业务口径。

## 接口与数据结构

- `OrderProgressFilter` / `OrderProgressQuery` 增加 `unpaid`。
- 不新增订单字段、API 写接口、D1 表或迁移；错失筛选只读取前端现有订单快照。

## 实现方案

1. 在 `app/calculator.ts` 增加 `getOrderShortPasses`，按每个已选串关的“所需关次 − 已确认命中场次数”计算差关次数；未确认和明确未命中都计入差关，不要求剩余场次可补齐。
2. 在 `FootballApp.tsx` 添加 `orderShortPassFilters`，使用与手动添加订单一致的输入框和下拉网格；本地过滤按所选差关次数与 `getOrderShortPasses` 的交集判断。
3. 在订单进度选项中加入 `unpaid`，本地通过 `isOrderPaid` 判断；云端将其映射为 `payment_status = 'unpaid'`。
4. 保持云端查询只传递日期、未支付/未结账进度和订单状态；差关次数选择不触发云端请求，由前端对当前订单快照过滤。
5. 在测试中覆盖无失败、部分失败、整体失败、未确认、8 串 1 差 1/2 关、多选 OR、超过实际比赛数和未选比赛不计入等情况。

## 兼容与发布影响

- 历史订单无需迁移；支付状态已有默认值 `unpaid`，旧快照缺少命中和失败列表时按当前订单快照计算差关次数。
- 不改变“成功 / 有希望 / 失败”的订单状态计算，也不改变批量支付、判断和结账行为。

## 实施结果

- 订单进度新增“未支付”，游客本地按 `paymentStatus` 判断，云端按 `payment_status` 查询；可与日期、结账进度和订单状态条件叠加。
- 订单筛选保留“错失”字段，选项改为“差1关”至“差8关”；筛选按订单中任一串关距离全部确认命中还差的场次数保留订单，未确认和未命中均计入，不排除已无法组成的串关。
- 桌面端将订单日期、订单进度、订单状态和错失压缩到同一筛选行；错失使用与手动串关快捷项一致的两列下拉网格，移动端在窄屏下自动单列。
- 错失筛选使用前端现有订单快照，不触发云端查询；未支付筛选使用已有 `payment_status` 字段，不新增数据库迁移。
- `isOrderFailed` 保持基于失败场次的整体失败语义；差关筛选使用独立的“串关场次/已确认命中”计算。
