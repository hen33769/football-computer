# 主客队展示与订单税额 Research

## 需求边界

- `TeamNameWithIcon` 与内部 `TeamNameWithAlias` 不再使用 `iconPosition`、`aliasPosition` 或解析结果中的 `aliasBefore`，统一传入 `teamPosition: "home" | "away"`，组件依据主客队位置决定队徽、主名、标签和别名的排列。
- 订单新增可持久化、可手动修改的税额字段；已结账订单也允许修改税额。
- 赛果判断后按奖金自动计算税额，并与赛果一同保存。
- 订单页筛选盈亏、累计收入、利润趋势和相关提示统一按扣税后的收入计算，同时显示税额。
- 本阶段只完成 Research，不修改业务代码、迁移或测试。

## TeamNameWithIcon 现有实现

- `app/components/TeamNameWithAlias.tsx`
  - `TeamNameWithIcon` 当前公开 `iconPosition?: "before" | "after"` 与 `aliasPosition?: "before" | "after" | "auto"`。
  - 当前默认布局相当于主队：别名在主名前、队徽在整段名称后。
  - 客队调用方需要同时传 `iconPosition="before" aliasPosition="after"`，否则容易出现两个参数只改一个、布局不一致的问题。
  - 新增球队标签后，`betweenNames` 位于主名与别名之间；主客队方向切换时仍需保持 tag 在两种名称之间。
- 共有 6 个 `TeamNameWithIcon` 调用点：
  - `app/FootballApp.tsx` 的订单/比赛标题与投注页主客队；
  - `app/FootballInsights.tsx` 的官方趋势和赛事前瞻标题。
- `TeamNameWithAlias` 没有组件外调用者。复核发现 `resolveTeamNameDisplay` 的 `aliasBefore` 在命中名称组时始终为 `true`，未命中时虽为 `false` 却没有别名，因此它不表达有效业务状态。按后续确认删除 `aliasBefore` 和 `TeamNameAliasPosition`，由 `teamPosition` 唯一决定排列。

## TeamNameWithIcon 建议方向

- 将 `teamPosition` 设为必填，所有调用点显式传 `home` 或 `away`，避免未传参数时默认为某一侧而掩盖调用错误。
- 组件内固定映射：
  - `home`：`别名 → tag → 主名 → 队徽`；没有别名时为 `主名 → tag → 队徽`。
  - `away`：`队徽 → 主名 → tag → 别名`。
- 删除 `TeamNameWithIcon` 的 `iconPosition`、`aliasPosition` 公共参数，并让 `TeamNameWithAlias` 也接收必填 `teamPosition`；删除解析结果中的 `aliasBefore`，保留查询高亮与 `betweenNames`。
- 该调整不改变球队别称解析、标签匹配或数据结构，只收口展示 API。

## 订单奖金与账本现状

- `app/types.ts` 与 `app/order-model.ts`
  - `SavedSlip` / `CompactOrder` 只保存汇总奖金 `settledPrize`，没有税额。
  - `compactOrderSummary`、模型互转和导入校验都只识别奖金。
- `app/calculator.ts`
  - `calculateCurrentPrize` 会遍历串关组合和中奖选项，先计算每个组合奖金，再汇总成整张订单奖金。
  - 对外只返回汇总金额，不保留每注或每个中奖组合的金额明细。
  - 奖金计算已有“银行家舍入”到分；云端金额通过 `toCents` 以整数分保存。
- `app/results.ts` 与 `app/FootballApp.tsx`
  - 一键判断通过 `judgeLoadedOrdersWithResults` 写入命中、赛果、比分、赔率与失败场次，目前不写奖金。
  - 订单明细手动保存命中走普通订单更新，也不写奖金。
  - 结账时前后端都会重新执行 `calculateCurrentPrize`，此时才写入 `settledPrize`。
  - 已结账订单的投注结构和赔率被冻结，但普通订单更新仍允许名称、时间等非投注字段变化，已有 `updatedAt` 并发检查。
- `db/schema.ts` 与 `app/server/orders-service.ts`
  - `user_orders` 同时保存完整 `data_json` 和供查询/汇总使用的 `settled_prize_cents`。
  - 新税额若只写 JSON，财务 SQL 需要逐行解析 JSON；按现有设计应新增独立的整数分列，并确保它与 JSON 同步写入。
- `app/imports.ts`、`app/server/finance-service.ts` 与 `app/finance-trend.ts`
  - 筛选收入对已支付且成功的订单取“已结账奖金与实时奖金的较大值”。
  - 累计收入、订单账本、导入合并差额、云端财务汇总和趋势图目前均直接累计税前 `settledPrize`。
  - 筛选盈亏 tooltip 目前只有“已支付”和“筛选收入”；累计收入副行显示“订单收入 + 纠错”。

## 税额数据与计算建议

- 在订单模型中增加可选 `taxAmount`（页面/JSON 单位为元），D1 增加 `tax_cents`（单位为分）。奖金继续表示税前奖金，不修改 `settledPrize` 的含义。
- 增加单一纯函数统一计算自动税额，并让前端预览、赛果判断、结账兜底和服务端校验复用，避免各路径出现不同阈值或舍入口径。
- 建议把“未保存税额”和“明确改成 0”区分开：
  - `taxAmount === undefined` 表示历史数据或尚未计算，可以按规则补算；
  - `taxAmount === 0` 表示已经保存或用户明确覆盖为 0，不应被普通编辑/结账无条件改回自动值；
  - 再次判断赛果属于重新计算事件，可用最新奖金覆盖税额。
- 税额编辑放在现有“编辑订单”弹窗，独立于投注结构、倍率和结账锁定状态，只在保存请求期间禁用。这样未支付、已支付、已结账订单都使用同一入口，并继续受订单版本冲突保护。
- 服务端应校验税额为有限、非负、最多两位小数；是否允许税额大于奖金需要确认。建议禁止大于奖金，避免出现负收入。
- 筛选统计建议拆成税前奖金、税额、税后收入三个值：
  - `筛选税后收入 = 符合现有口径的成功已支付订单奖金 - 对应税额`；
  - `筛选盈亏 = 筛选税后收入 - 已支付金额`；
  - tooltip 显示“已支付 / 税前奖金 / 税额 / 税后收入”。
- 累计收入、订单账本和趋势图的 `income` 统一表示税后收入；累计收入卡片副行增加税额汇总。云端 `/api/finance` 需要返回订单税额合计，游客模式则从本地订单计算。
- 订单卡片和明细建议同时显示“税前奖金、税额、税后收入”，避免“已中奖”与“累计收入”数值不同却没有解释。单笔结账、批量结账、撤回结账及删除订单的确认文案也应改用税后入账金额并列出税额。

## 数据库与兼容影响

- 当前工作区已有尚未发布的 `0008`～`0010` 迁移；本需求应新增 `drizzle/0011_*.sql`，不改写已有迁移。
- `user_orders.tax_cents` 应允许 `NULL`，用于区分历史未计算与用户明确保存的 0。
- 订单模型互转、云端读写、批量事务、导入导出校验和游客本地存储都需支持新字段；旧 JSON 缺字段仍应正常读取。
- 云端财务查询、趋势查询和订单写入的冗余列必须同步更新。批量操作仍需维持整批成功或整批回滚，税额编辑仍需检查 `updatedAt`。
- 如果历史订单需要立即按新规则扣税，迁移不能只增加列：还要为已保存奖金的订单回填 `tax_cents`，并同步补写 `data_json.taxAmount`，否则页面订单与财务汇总会出现两个口径。

## 已确认口径

- 阈值按整张订单的汇总奖金判断；必须严格大于 `10000.00` 元，`10000.01` 元开始计税。
- 超过阈值后，对全部奖金按 20% 计算税额；金额最终按分舍入。
- 只有“已结账且成功”的订单税额才参与实际账本、筛选盈亏、累计收入和趋势；赛果判断阶段可先计算并保存预计税额，结账后才影响收入。
- 页面“累计收入”改名为“累计税后收入”。筛选盈亏 tooltip 显示已支付、税前奖金、税额和税后收入；累计税后收入卡片副行增加订单税额合计。
- 已结账且成功、奖金超过阈值的历史订单需要回填税额，并同步改变累计税后收入与历史趋势。
- 普通编辑和结账保留手动税额；再次执行赛果判断时按最新奖金重新覆盖税额。税额不能小于 0，也不能大于奖金。

## 风险与验证重点

- 税额同时存在于订单 JSON 和 D1 冗余列，必须验证创建、编辑、判断、结账、撤回、删除、导入和批量事务后两处一致。
- 税额改变后云端财务接口会影响累计收入与利润；游客模式也必须同步调整本地累计值，不能只更新订单卡片。
- 筛选收入包含未结账但已支付成功的订单，而累计收入只包含已结账订单；两处使用相同扣税函数，但保留现有入账时机差异。
- 已结账税额编辑会改变历史结账日的趋势数据和当前累计收入，需要验证刷新后仍一致。
- 需要覆盖 `9999.99`、`10000.00`、`10000.01`、手动改为 0、税额两位小数、旧订单缺字段，以及并发冲突和批量回滚。
- `TeamNameWithIcon` 需在投注卡片、订单标题、官方趋势和赛事前瞻中验证主客队排列；桌面端和移动端均检查别名、tag、图标同时存在的情况。

## 预计验证范围

- 单元测试：税额阈值、精度、模型往返、筛选税后盈亏、账本与趋势；主客队排列所依赖的映射。
- 服务测试：自动判断写税、结账兜底、结账后改税、历史兼容、权限、并发冲突、批量原子性和财务汇总。
- 数据迁移：在本地 D1 验证新增列、历史回填策略和 JSON/列一致性。
- 浏览器：桌面端与移动端检查订单编辑、判断赛果、结账、撤回、筛选 tooltip、累计收入副行、趋势 tooltip 和球队名称布局，并检查控制台错误。
- 完整检查：`npm test`、`npm run lint`、`npm run build`。
