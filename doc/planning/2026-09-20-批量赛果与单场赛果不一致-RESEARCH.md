# 批量赛果与单场赛果不一致 Research

日期：2026-09-20

## 问题现象

- 订单页“获取全部赛果”将伊朗亚运男足 VS 中国亚运男足（比赛 ID `2041586`）归为“未结束或暂无赛果”。
- 同一场比赛点击单场“获取赛果”可以成功填充 5 个玩法。
- 用户提供的批量接口响应确实包含 `2041586`，因此不是日期范围、分页、比赛 ID 标准化或目标 ID 过滤遗漏。

## 相关实现

- `app/FootballApp.tsx` 的 `fetchAllMatchResults` 调用 `fetchSportteryUniformMatchResults`，使用按日期批量赛果接口；记录没有可解析比分时累计为 `unfinishedCount`。
- 同文件的 `requestMatchResult` 调用 `getMatchScoreV1.qry` 和 `getFixedBonusV1.qry`；确认 `matchPhaseTc` 已结束后，从单场比分生成赛果。
- `app/sporttery.ts` 的 `parseSportteryUniformMatchOutcome` 只有在批量记录的 `sectionsNo999` 可解析为全场比分时才返回 `completed`，否则返回 `unfinished`。
- 现有测试已覆盖批量记录无比分时归类为 `unfinished`，当前代码行为与既定规则一致。

## 接口证据

用户提供的批量响应：

- `matchId`: `2041586`
- `matchResultStatus`: `"1"`
- `poolStatus`: `"Close"`
- `sectionsNo1`: `""`
- `sectionsNo999`: `""`
- 批量数据 `lastUpdateTime`: `2026-09-20 09:25:02`

2026-09-20 15:40（Asia/Shanghai）直接复核体彩官方接口：

- 批量接口带额外缓存破坏参数后，响应头为缓存 MISS，但上述记录和 `lastUpdateTime` 仍未变化；可排除浏览器/CDN 旧缓存。
- 单场比分接口对 `2041586` 返回 `matchPhaseTc: "14"`、`matchPhaseTcName: "比赛结束"`、`matchStatusName: "直播结束"`，半场和常规时间比分均为 `0:0`。
- 固定奖金接口也已返回 `sectionsNo999: "0:0"`。

## 根因

体彩官方两个数据源更新不同步：按日期批量赛果接口仍保留该场的未出结果记录，而单场比分接口已经发布完赛阶段和比分。应用的一键流程只信任批量源，不会对“批量记录存在但比分为空”的比赛回退到单场接口，因此出现一键获取不到、单场可以获取的差异。

这不是本地缓存、分页、日期或 ID 匹配问题，也不是 `0:0` 被误判为空：单场解析和现有测试均能正确保留 `0:0`；批量响应里对应字段是真正的空字符串。

## 建议修复方向

- 保留批量接口作为首选，继续获得低请求数和分页能力。
- 对批量结果中的 `unfinished` 以及完全缺失记录，仅针对已超过合理完赛时间的比赛调用现有单场 `requestMatchResult` 兜底，并保持串行/限速。
- 汇总通知区分“批量源暂未同步但单场兜底成功”和“单场也确认未结束/暂无比分”，避免把上游数据延迟误报成比赛未结束。
- 增加回归测试：批量记录存在但比分为空、单场阶段已结束且比分为 `0:0` 时，一键流程最终应成功；单场仍未结束时继续计入未结束。

## 约束与风险

- 不应直接把 `matchResultStatus: "1"` 当作已完赛，也不能在没有比分时伪造 `0:0`；必须由单场阶段和真实比分共同确认。
- 单场兜底会增加请求数，应只处理批量未解决项，并沿用现有请求间隔，避免恢复为所有比赛逐场请求。
