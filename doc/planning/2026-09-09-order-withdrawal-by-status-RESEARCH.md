# 订单按状态撤回 Research

## 相关实现

- `app/FootballApp.tsx`：订单卡片目前只在 `settledAt` 存在时显示“撤回”，并由 `withdrawOrderSettlement` 清除结账信息；已支付未结账订单只显示结账操作。
- `app/personal-sync.ts` 与 `app/FootballRoute.tsx`：本地订单直接应用订单增量，云端订单统一通过带操作类型的批量更新接口提交，并在成功后刷新订单和账本。
- `app/order-model.ts`：`paymentStatus` 区分未支付与已支付，`settledAt` 区分未结账与已结账；`BulkOrderOperation` 控制服务端对批量写入的语义校验。
- `app/server/orders-service.ts`：支付会冻结倍率，结账会记录 `oddsLockedBeforeSettlement`，撤回结账后恢复结账前的倍率锁定状态。批量更新在写入前校验全部订单版本和业务状态，再通过 D1 batch 整批提交。
- `tests/orders-service.test.ts`：已有支付、冻结与整批失败测试，可在同一层补充按状态撤回的服务端测试。

## 现有行为

- 未支付订单可支付；支付时计入支出并冻结投注与倍率。
- 已支付且已有判断结果的订单可结账；结账时计入收入。
- 已结账订单可撤回结账；撤回后仍保持已支付，但已支付未结账订单不能撤回支付。
- 云端普通 `update` 虽能提交订单快照，但没有专门的撤回业务校验，不能可靠防止客户端借撤回修改其它订单内容。

## 目标状态流

1. `已结账` 点击“撤回”：仅撤回结账，清除结账时间与奖金，订单回到 `已支付`。
2. `已支付、未结账` 点击“撤回”：撤回支付，订单回到 `未支付`，并从支出中扣除该订单投入。
3. `未支付` 不显示“撤回”。

因此同一张订单可以按 `已结账 -> 已支付 -> 未支付` 的顺序分两次撤回，不能一次跨越两个状态。

## 约束与风险

- 云端撤回必须继续使用订单 `id + updatedAt` 做并发校验，并由服务端根据当前持久化状态决定撤回类型。
- 撤回结账只回滚收入；撤回支付只回滚支出。云端账本由数据库重新汇总，本地访客账本需要显式更新。
- 支付前可能已手动锁定倍率。为精确恢复，需要在支付时保存 `oddsLockedBeforePayment`；历史已支付订单没有该字段时按未锁定处理。
- 新字段只保存在订单 JSON 中，现有 D1 列已经能表达支付与结账状态，不需要数据库迁移。
- 历史数据可能存在未支付却已结账的订单；撤回结账保持原支付状态，不凭空补记支付或支出。
- 云端重新加载筛选列表可能让刚撤回的订单消失；操作返回值仍需包含该订单的已提交版本，以便同步已打开的明细。

- 无。需求可由订单现有的结账、支付状态无歧义地决定撤回类型。
