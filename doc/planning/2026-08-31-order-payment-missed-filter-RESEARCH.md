# 订单未支付与差关筛选 Research

日期：2026-08-31

## 需求理解

- 订单页的“订单进度”单选增加“未支付”，按订单 `paymentStatus` 筛选。
- 订单筛选增加“错失”多选，选项为“差1关”至“差8关”，选择交互沿用串关选项的多选思路。
- “差 n 关”表示订单中某个已选串关距离全部确认命中还差 n 场；n 不是订单选择的 n 串 1。未确认和明确未命中的比赛都不计入已确认命中数，均计入差关数。
- 差关筛选不判断订单是否仍可中奖，也不排除已明确失败的订单；例如 8 串 1 已确认命中 7 场，最后 1 场未确认或未命中，都属于“差1关”。
- 多选差关次按 OR 关系筛选，选中任一差关次数即可保留订单。

## 当前实现

- `app/FootballApp.tsx` 保存订单页筛选状态，在本地通过 `filteredSavedSlips` 过滤；云端通过 `currentCloudOrderQuery` 交给订单 API 查询，错失条件不进入该查询。
- `app/api-client/orders.ts` 将订单查询编码为 `progress`、`status` 等 URL 参数；`app/api/orders/route.ts` 负责白名单解析。
- `app/server/orders-service.ts` 的 `ordersWhereClause` 使用 D1 `user_orders` 索引字段过滤已结账进度和订单状态。支付状态已持久化在 `payment_status`，无需新增字段。
- 订单快照中的 `passes` 保存串关数，`match_ids_json` 保存已投注比赛 ID，`failedMatchIds` 保存云端压缩订单中已失败的比赛；旧快照可能使用 `failedMatches`，但已存在解析兼容逻辑。
- `app/calculator.ts` 的 `isOrderFailed` 使用“失败比赛数导致剩余比赛不足以组成所有串关”的判定；订单页的差关筛选独立按“串关场次 − 已确认命中场次数”计算，不改变整体失败判定。
- 手动添加订单在 `app/FootballApp.tsx` 中使用 1 至 8 的串关快捷选项；订单筛选可复用同一组数值，展示文案改为“差 n 关”。

## 实现约束与风险

- 本次不改变订单数据结构、支付流程、结账流程或订单状态定义；“未支付”只是新增查询条件。
- 错失筛选明确只在前端执行，不把差关次数加入云端查询参数；云端仍按日期、进度和订单状态返回当前候选集，再由浏览器按订单快照判断。
- 前端差关筛选必须不能只判断订单整体失败，也不能把未选中的比赛计入已确认命中或差关场次；已经全部确认命中的串关不计为“差0关”。
- 订单进度的“未支付”与“未结账”可以同时存在，前者按 `payment_status = 'unpaid'`，后者按 `settled_at IS NULL`，两者叠加时取交集。

## 预计影响文件

- `app/calculator.ts`：增加差关次数的纯函数判定。
- `app/FootballApp.tsx`：增加筛选状态、本地过滤和手动串关风格的“差 n 关”多选控件；扩展“未支付”进度选项。
- `app/api/orders/route.ts`：接受 `unpaid` 进度值。
- `app/server/orders-service.ts`：扩展 D1 WHERE 条件，增加未支付过滤。
- `tests/calculator.test.ts`：覆盖差关次数判定和多选口径。

## 验证重点

- 未支付筛选只返回 `paymentStatus` 为未支付的订单；与已结账/未结账组合时结果正确。
- 1 至 8 关次选项可多选，选项标签为“差1关”至“差8关”，清除后恢复不限。
- 4 场订单选择 2、3 串 1，已有 1 场确认命中时，返回“差1关、差2关”；已有 2 场确认命中时只返回“差1关”，其余比赛无论未确认还是未命中均照此计算。
- 差关次数只由已确认命中数决定，明确未命中和未确认都属于未命中/未确认场次；不再以剩余场次是否足够补齐作为筛选条件。
- 云端候选订单与本地错失筛选口径一致，且不新增 D1 迁移。
