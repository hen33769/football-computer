# 收入纠错税额 Research

日期：2026-10-29。状态：Research 结论已确认；实现与验证状态见对应 Planning。

## 需求理解

- 纠错类型在产品文案中统一为“支出”和“收入”，不再把类型显示为“税后收入”。
- 选择收入时增加税额输入，并让税额进入记录、累计统计、趋势和完整备份，而不是只作为表单备注。
- 继续沿用现有差值流水、可选归属日期、备注、补差、归档账本和游客／云端一致语义。

当前最大的实现歧义是：收入表单中的金额代表税前收入还是税后收入。该选择会直接决定累计收入、利润、趋势和补差的计算方式，必须先确认。

## 推荐业务口径

### 推荐：收入填写税前差值，税额填写税额差值

选择“收入”时显示两个带正负号的字段：

- 收入差值（税前）
- 税额差值

该笔记录的税后净影响为：

`税后收入差值 = 税前收入差值 - 税额差值`

示例：收入 `+200`、税额 `+20`，累计税前收入增加 200，累计税额增加 20，累计税后收入和利润增加 180。

推荐原因：

- 与现有订单的“税前奖金 − 税额 = 税后收入”口径一致。
- 页面可以完整解释累计税前收入、累计税额和累计税后收入。
- 税额不只是审计备注，会真实影响利润和趋势。

### 税额也应采用差值

- 税额允许正数增加、负数减少，默认 0，不自动按 20% 计算。
- 补差时收入和税额都留空，由用户填写本次差值；原类型、日期和关联关系仍自动带出。
- 示例：原来收入 `+200`、税额 `+20`，实际应为收入 `+180`、税额 `+18`，补差填写收入 `-20`、税额 `-2`。
- 建议允许“收入差值为 0、税额差值非 0”，以支持只修正税额；两者同时为 0 才拒绝。

### 最终余额校验

建议校验当前 active 账本的三个最终值，而不是限制单条记录的正负组合：

- 最终累计税前收入不得小于 0。
- 最终累计税额不得小于 0。
- 最终累计税后收入不得小于 0；等价于累计税额不能超过累计税前收入。
- 支出继续只校验最终累计支出不得小于 0。

不建议强制单条记录中税额与收入同号或税额绝对值不超过收入绝对值，因为补差是差值流水，合法的历史修正可能出现不同方向；表单可提示异常组合，但最终累计校验才是可靠约束。

## 推荐数据与兼容方案

### D1 迁移

新增 `0014_finance_correction_tax.sql`，不修改已发布的 0013：

- `user_finance_correction_entries.tax_delta_cents INTEGER NOT NULL DEFAULT 0`
- `user_finance_correction_entries.tax_correction_before_cents INTEGER NOT NULL DEFAULT 0`
- `user_finance_correction_entries.tax_correction_after_cents INTEGER NOT NULL DEFAULT 0`
- `user_finance_corrections.income_tax_correction_cents INTEGER NOT NULL DEFAULT 0`

继续保留现有 `delta_cents` 为“对最终税后收入／支出的净影响”：

- 支出记录：`delta_cents = 支出差值`，税额为 0。
- 收入记录：`delta_cents = 税前收入差值 - 税额差值`。
- 收入记录的税前差值可由 `delta_cents + tax_delta_cents` 无损推导，不需要再存一列重复值。
- 现有记录和旧迁移记录自动得到税额 0，因此原税后收入、利润、趋势和账本汇总完全不变，不需要重写正式流水。

汇总表继续缓存税后收入纠错，同时新增纠错税额汇总；纠错税前收入汇总可由两者相加得到。每次新增和导入后校验三项汇总与 active 流水一致。

### API 兼容

- 新页面建议 POST `amountDeltaCents`（支出差值或税前收入差值）和 `taxDeltaCents`。
- 响应记录同时返回 `amountDeltaCents`、`taxDeltaCents`、`netDeltaCents`；可暂时保留 `deltaCents` 作为 `netDeltaCents` 的兼容别名。
- 旧客户端只发送 `deltaCents` 时，按税额 0 的旧税后净值处理一个兼容周期，避免部署后已打开的旧标签页立即失败。
- requestId 的同内容判断必须加入税额，防止相同 requestId 用不同税额重试时被错误视为同一请求。
- 旧绝对值 PATCH 继续只调整税后收入纠错，生成税额 0 的 legacy-client 流水；不能从旧绝对值自动推断税额。

### 完整备份与游客账本

- 建议完整备份升级到 v7，记录新增 `taxDeltaCents`，财务汇总新增 `incomeTaxCorrectionCents`；v5／v6 导入统一补税额 0。
- 不建议悄悄扩展 v6：旧版本会忽略新税额并在恢复后改变税后结果，存在隐性数据丢失风险。
- v7 稳定来源冲突比较、摘要、合并初值、覆盖恢复和汇总一致性都必须包含税额。
- 游客账本升级到 v3；读取 v2 时给所有记录补税额 0、税额 before／after 0，保持 revision 和稳定来源 ID，不重复迁移。

## 前端与趋势建议

### 新增／补差表单

- 类型选择固定显示“支出／收入”。
- 支出显示一个“支出差值”；收入显示“收入差值（税前）”和“税额差值”。
- 税额字段默认 0，明确提示“正数增加税额，负数减少税额，不自动计算”。
- 收入预览展示当前及调整后的税前收入、税额、税后收入，并明确本次税后净影响。
- 历史收入记录展示税前差值、税额差值、税后净差值；旧记录显示税额 0。

### 统计卡片

- 主数字继续使用“累计税后收入”。
- 副行建议统一展示：订单税前收入、收入纠错（税前）、订单税额、纠错税额、累计税后收入中的纠错净值。
- 云端和游客从相同字段推导，避免再次出现两套口径。

### 趋势

- 有日期纠错把税前收入差值和税额差值归入对应日期；无日期的两者都进入初值。
- 趋势的当日／累计税额应为订单税额加纠错税额。
- 当日税后收入与利润使用 `订单税后收入 + 纠错税前收入 - 纠错税额`。
- tooltip 建议拆成订单税前收入、收入纠错（税前）、订单税额、纠错税额、税后收入合计，保留现有订单／纠错支出拆分。

## 风险与验证重点

- 最大风险是把旧税后收入纠错重新解释为税前值，导致历史利润变化；推荐方案通过旧记录税额 0 避免该问题。
- 税额参与 requestId 幂等、稳定来源冲突和备份摘要，遗漏任一处都可能静默跳过不同税额的记录。
- 合并备份的历史初值策略需要同时处理税后净初值和税额初值，不能只补收入差值。
- 补差引用旧 v6／v2 记录时必须保持有效；旧记录的税额按 0 展示。
- 必须覆盖税额正负差值、只改税额、税额超过最终税前收入、全局税额变负、日期初值、归档账本、重复导入和失败回滚。
- 页面交互需验证收入／税额的正负输入、补差、预览、记录、统计和趋势在桌面与移动端一致。
- 这是新增行为和备份格式升级，后续发布应使用 minor 版本；正式迁移前需再次确认 D1 `smgr-cloud` 和生产范围。

## 已确认结论

### A1：收入采用税前差值

收入表单中的“收入差值”表示税前收入差值。填写收入 `+200`、税额 `+20`，最终税后收入增加 `+180`。

### A2：税额采用带符号差值

税额支持正数增加和负数减少。例如原收入 `+200`／税额 `+20`，实际应为收入 `+180`／税额 `+18`，补差填写收入 `-20`、税额 `-2`。

### A3：允许只纠正税额

允许收入差值填写 `0`、只填写非零税额差值；收入和税额同时为 0 时拒绝保存。
