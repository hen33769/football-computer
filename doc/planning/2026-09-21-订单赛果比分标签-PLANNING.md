# 订单赛果比分标签 Planning

## 已确认口径

- 普通比分 tag 只显示具体比分，例如 `0:1`，不显示“比分”前缀。
- “其他”比分显示类别与具体比分，例如 `胜其他 6:0`、`平其他 4:4`、`负其他 0:6`。
- 历史订单缺少具体比分时，只将内部 ID 改为中文“胜其他 / 平其他 / 负其他”，不做赛果补数。

## 数据与兼容设计

- 在 `SavedSlip` 和 `CompactOrder` 增加可选的 `resultScores`，按订单比赛 ID 保存 `{ home, away }`全场比分。
- 保留 `resultValues.score = winOther | drawOther | loseOther | 具体比分` 的现有玩法命中语义，不改动 `hits`、订单状态或奖金计算。
- `resultScores` 随现有 `user_orders.data_json` 持久化，不新增 D1 字段或迁移。
- 新字段为可选字段；旧订单仍可加载、编辑、判定和结账。

## 实施步骤

1. 扩展订单类型和紧凑模型，实现比分映射的深拷贝、往返转换与输入验证。
2. 在 `judgeSlipWithResults` 中同步保存 `MatchResult.fullScore`，并把比分映射纳入“订单是否真正发生变化”的比较。
3. 更新本地订单验证、订单重新保存时的按比赛过滤，以及独立赛果保存 API 的可选字段，避免后续编辑丢失数据。
4. 新增统一的订单比分文案格式化函数，不再依赖订单是否投注了该比分选项。
5. 同步更换订单卡片和订单明细的比分 tag，保留现有颜色和布局。
6. 补充赛果判定、历史兼容、模型往返和文案格式化测试。

## 验证方式

- 定向单元测试：`tests/calculator.test.ts`、`tests/orders-service.test.ts` 以及新增的纯函数用例。
- 全量验证：`npm test`、`npm run lint`、`npm run build`。
- 浏览器验证：桌面端和移动端各检查普通比分、有具体比分的“其他”、无具体比分的历史“其他”，并确认控制台无新增错误。

## 发布影响

- 这是用户可见的订单展示调整，按仓库规则属于 `minor`。
- 与后续赛果赔率标签改动合并按 `minor` 发布为 `v1.31.0`；只更新应用代码和订单 JSON 兼容字段，不执行 D1 迁移或历史订单重写。
