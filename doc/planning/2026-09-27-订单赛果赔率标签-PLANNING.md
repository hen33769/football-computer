# 订单赛果赔率标签 Planning

## 已确认口径

- 订单卡片和订单明细的半全场赛果 tag 不显示“半全场”前缀。
- 比分和半全场 tag 展示官方 `matchResultList.odds` 中的赛果固定奖金，例如 `1:1 @5.75` / `负平 @16.50`。
- 官方赛果赔率仅用于 tag 展示，不覆盖订单已投注赔率，不参与订单奖金计算。
- 赔率获取失败不阻断赛果判定，tag 只显示赛果文案。
- 不自动补齐历史订单；只有今后新获取并保存的赛果显示赔率。

## 数据与兼容设计

- 在 `MatchResult` 中增加可选的按玩法赔率映射，用于从官方赛果流转到订单判定。
- 在 `SavedSlip` 和 `CompactOrder` 中增加可选的 `resultOdds`，按订单比赛 ID 和玩法保存大于 0 的有限数值。
- `resultOdds` 随现有 `user_orders.data_json` 持久化，不新增 D1 字段或迁移。
- 新字段保持可选；旧订单、手动赛果和官方赔率缺失时继续使用无 `@...` 的展示。

## 实施步骤

1. 扩展赛果与订单类型，补齐深拷贝、导入验证、紧凑模型往返和独立赛果保存 API。
2. 增加 fixed-bonus 详细解析，同时生成中奖选项 ID 和按玩法的官方赛果赔率；保留现有只返回 ID 的兼容函数。
3. 单场和批量赛果获取同步读取 fixed-bonus；批量路径使用有界并发，失败仅记录赔率缺失。
4. `judgeSlipWithResults` 在保留 `resultValues` 和 `resultScores` 的同时写入 `resultOdds`，并将新字段纳入变更比较。
5. 统一赛果 tag 文案格式：有赔率时显示两位小数，半全场去掉前缀，订单卡片与明细使用同一口径。
6. 补充 fixed-bonus 解析、赛果判定、订单模型往返、历史兼容和文案格式测试。

## 实施结果

- fixed-bonus 详细解析现在同时保留中奖选项 ID 和官方赛果赔率，批量获取使用有界并发；赔率请求失败不会把已取得的赛果标记为失败。
- `MatchResult`、`SavedSlip` 和 `CompactOrder` 已支持可选赛果赔率，并补齐了云端订单转换、验证和独立赛果保存链路。
- 订单判定会同时保存具体比分和赛果赔率，但订单已投注选项的赔率和奖金计算逻辑未改动。
- 比分 tag 现在支持 `1:1 @5.75` 和 `胜其他 6:0 @250.00`；半全场 tag 支持 `负平 @16.50` 并已移除“半全场”前缀。无赔率的旧订单保持只显示赛果文案。
