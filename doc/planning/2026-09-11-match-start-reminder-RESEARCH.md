# 开赛提醒 Research

日期：2026-09-11

## 需求理解

- 对当前公共比赛列表中的比赛按实际开赛时间判断；比赛距离开赛大于 0 分钟且不超过 30 分钟时，属于“准备开赛”。
- 每次完整进入应用后检查一次；页面持续打开时继续定时检查，并在浏览器标签页从后台恢复可见时立即补检。
- 应用内“投注 / 订单 / 设置”切换不作为新的检查触发源；但驻留定时器不因切页停止。
- 同一场比赛在同一浏览器中只弹一次。本地记录在对应开赛时间到达后清理。
- 一次检查发现多场新比赛时，在同一个全局弹窗中按开赛时间列出；已经提醒过的比赛不重复列入后续弹窗。
- 已有开赛提醒未关闭而又出现新的待提醒比赛时，只关闭并替换“开赛提醒”本身，不关闭赛事详情、订单编辑、登录或版本更新等其它弹窗。
- 投注页中处于同一 30 分钟窗口的比赛卡片增加蓝色阴影；到达开赛时间后沿用现有逻辑转为停售并移除蓝色阴影。

## 当前页面与生命周期

- `app/page.tsx`、`app/orders/page.tsx` 和 `app/settings/page.tsx` 都进入同一个 `FootballRoute`；`FootballRoute` 完成公共比赛、账号和公共队名数据的 bootstrap 后才渲染 `FootballApp`。
- `FootballRoute` 用 `activeView` 和 History API 完成内部切页。`FootballApp` 的 `activeView` 只是 `initialView` 属性的当前值，投注、订单、设置切换不会因为路由变化而卸载组件；只有账号 key 变化会重建 `FootballApp`。
- 因此提醒应放在 `InnerFootballApp`：这里同时持有最新 `matches`、Ant Design `App` 的 modal 上下文和贯穿内部切页的生命周期。放在 `FootballRoute` 会拿不到投注页刷新后的比赛状态；放在投注视图 JSX 内则不能覆盖订单页和设置页。
- `FootballRoute` 已有每分钟版本检查和 `visibilitychange` 恢复检查，可作为待机恢复处理的现有范式。
- `FootballRoute` 的账号登录遮罩和版本强制刷新遮罩分别使用 `z-index: 2000`、`2400`，高于普通 Ant Design Modal。若提醒在它们后面打开并立即记录为已提醒，用户可能没有看到提醒却被永久去重；这两类阻塞层存在时应暂停提醒检查且不写记录，解除后再补检，而不是提高提醒层级抢占登录或版本刷新。
- `FootballApp` 已有一个每 30 秒更新的 `saleClock`。它在所有内部视图持续运行，并在比赛到达开赛时间时把比赛改为停售、清除选择；开赛提醒与卡片阴影可复用这个时钟，避免新增另一套常驻轮询。
- 投注页进入后还会立即拉取一次比赛，并按时段自动刷新。提醒检查必须也响应 `matches` 更新，否则首次缓存为空、稍后才取得比赛时会漏报；这属于数据就绪检查，不是内部切页触发。

## 比赛时间与数据口径

- `MatchItem.date` 是体彩业务日，不一定等于实际开赛自然日；`MatchItem.time` 通常是官方 `matchDate + matchTime` 转成的完整 `YYYY-MM-DD HH:mm`。提醒必须以 `time` 中的实际日期时间为准，只有历史数据只含 `HH:mm` 时才回退拼接 `date`。
- `app/sporttery.ts` 的 `hasMatchStarted` 已按上述规则解析开赛时间；`FootballApp.tsx` 的 `parseMatchDateTime`/`formatMatchCardTime` 另有一份等价解析。新增提醒时不应再复制第三份时间解释。
- 建议抽取并导出一个返回开赛时间戳的纯函数，让 `hasMatchStarted`、提醒窗口和页面时间格式共同复用，保证“阴影消失、提醒记录清理、比赛停售”使用同一边界。
- 推荐窗口采用半开闭区间 `now < kickoff <= now + 30 分钟`：恰好 30 分钟时提醒，恰好开赛时不提醒并清理记录。
- 推荐按全部公共比赛判断，不受当前投注页日期、销售状态、联赛筛选和卡片折叠影响。开赛提醒表达的是赛事时间而不是销售状态；只要比赛有合法未来开赛时间就应纳入。订单快照中的历史比赛和手动订单临时投注不应作为提醒来源。

## 数据来源与持久化

- 公共比赛由 `FootballRoute.bootstrap` 从 `/api/matches/current` 取得并写入现有本地比赛缓存；投注页刷新后由 `applySportterySnapshot` 合并到 `matches`。不需要新增 API、D1 字段或迁移。
- `app/browser-storage.ts` 已提供带内存降级的 `localCache`，Safari 配额或权限异常时页面仍可工作。提醒记录应复用它，而不是直接调用 `window.localStorage`。
- 建议在 `CLOUD_STORAGE_KEYS` 增加独立、版本化的 key，例如 `football-simulator-match-start-reminders-v1`。虽然常量名含 `CLOUD`，目前公共比赛和游客数据也统一从这里取 key。
- 不建议只持久化 ID 数组。比赛缓存只保留约 7 天；如果用户长时间未打开页面，比赛本体可能先被缓存清理，之后无法再通过比赛列表判断该 ID 是否已开赛。
- 推荐保存为“标准化比赛 ID -> 提醒时确认的开赛时间戳”。每次检查先删除时间戳小于等于当前时间、格式无效的记录，再判断新比赛。这样无需依赖旧比赛仍在缓存，也能在已提醒比赛后来延期时于原时间记录过期后，按新的开赛时间重新进入提醒窗口。
- 记录应是浏览器级而非账号级：公共比赛本身不属于账号，登录、退出或游客/云端切换不应造成重复提醒。Web Storage 写入失败时，`localCache` 会在当前页面生命周期内以内存记录保证不重复。

## 推荐实现结构

- 新增 `app/match-start-reminder.ts`：放置 30 分钟常量、开赛时间解析、窗口判断、提醒记录校验/清理和新提醒比赛筛选等纯函数；比赛 ID 统一使用现有 `normalizeSportteryMatchId`。
- `app/sporttery.ts`：让 `hasMatchStarted` 复用统一开赛时间解析；保持现有停售边界不变。
- `app/cloud.ts`：增加提醒记录的 local storage key。
- `app/FootballApp.tsx`：
  - 在 `InnerFootballApp` 维护当前开赛提醒实例或受控状态，使用最新公共 `matches` 和 `saleClock` 检查；依赖中不包含 `activeView`。
  - 由 `FootballRoute` 传入账号/版本阻塞层是否开启；阻塞期间不弹、不记已提醒，解除后再检查。
  - 在挂载/比赛就绪时检查，在现有 30 秒 clock 更新时检查；给 clock 增加标签页恢复可见时的立即更新时间，以补偿后台定时器节流。
  - 检查时先持久化本批新比赛，再打开弹窗，确保 React 开发模式重复 effect、登录导致的组件重建或快速刷新不会重复提醒。
  - 新批次到来时仅销毁已有的开赛提醒实例，然后打开只含本批新比赛的新弹窗；不要使用 `Modal.destroyAll()`，避免误关其它业务弹窗。
  - `MatchCard` 根据统一窗口判断增加 `starting-soon` class。
- `app/globals.css`：增加开赛提醒列表的桌面/移动布局，并为 `.match-card.starting-soon`、其 hover 状态设置明确的蓝色阴影；已有选中态左侧红色标识仍保留，蓝色阴影作为开赛优先级覆盖普通/选中/hover 阴影。
- 新增 `tests/match-start-reminder.test.ts` 并加入 `package.json` 显式测试清单；避免把时间、存储兼容和去重逻辑埋在 React effect 中而无法精确验证。

## 弹窗信息建议

- 标题使用“开赛提醒”，正文顶部显示“以下比赛将在 30 分钟内开赛”。
- 每场展示“周次场号、联赛、主队 VS 客队、实际开赛时间”；按开赛时间、场号排序。可附检测当下的“约 N 分钟后”，但以绝对时间为主，避免弹窗长时间未关闭后倒计时文案失真。
- 使用明确的“知道了”按钮并保留关闭图标；弹窗一出现即视为已提醒，关闭方式不影响去重。
- 不建议提醒时自动切换到投注页、清空筛选、展开日期分组或滚动到卡片。这些动作会打断订单/设置页工作，也与“页面内切换不需要”的边界冲突；蓝色阴影只在用户实际看到对应投注卡片时提供辅助定位。

## 边界、风险与验证重点

- 无效或缺失的 `time` 必须跳过，不能用业务日午夜误报。
- 单次多场、恰好 30 分钟、恰好开赛、已开赛、重复 ID、ID 前缀标准化、损坏/旧版存储值和延期后的再次提醒都应有纯函数测试。
- 需验证首次打开已有缓存、首次缓存为空后异步取得比赛、页面持续驻留进入 30 分钟窗口、标签页后台后恢复、登录导致组件重建和内部视图切换等路径。
- 需验证新批次出现时旧开赛提醒先被替换，且不会关闭或销毁其它 Ant Design modal。
- 需浏览器验证桌面端与移动端的多场列表、长队名、滚动、关闭按钮和控制台；卡片需验证普通、已选择、hover、即将开赛以及开赛后停售状态的样式优先级。
- 多个浏览器标签页会共享 localStorage，通常后检查的标签页会看到已记录 ID 而不提醒；两个标签页在同一瞬间检查仍存在非原子读写竞态。当前需求不值得为极小概率竞态新增 BroadcastChannel 协议，除非明确要求跨标签页严格只弹一次。

## 已确认结论

1. “准备开赛”只看合法的实际开赛时间，覆盖所有公共比赛，不受可售/待开售状态和当前投注筛选影响。
2. 已提醒比赛如果官方后来延期，允许它在原提醒时间记录过期、且新开赛时间再次进入 30 分钟窗口后重新提醒。

## 发布影响

- 本功能仅涉及前端公共比赛状态、本地浏览器存储和样式，不修改订单、赛果、财务、API 或 D1。
- 本次属于新增功能；若后续进入部署流程，应按 minor 从当前 `v1.26.0` 更新到 `v1.27.0`，并在同一发布提交中同步 `package.json`、`package-lock.json`、`APP_VERSION` 派生页面版本和 `UPDATE.md`。本次 Research 不调整版本、不更新 `UPDATE.md`，也不提交、推送或部署。
