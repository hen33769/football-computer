# 订单批量赛果与待结账筛选 Research

日期：2026-09-14

## 相关文件

- `app/FootballApp.tsx`：订单筛选、订单页赛果获取按钮、投注页自动批量赛果流程。
- `app/sporttery.ts`：体彩单场比分接口、按日期批量赛果接口、分页和赛果解析。
- `app/api-client/orders.ts`、`app/api/orders/route.ts`：云端订单查询参数。
- `app/server/orders-service.ts`：订单进度 SQL 筛选。
- `app/order-model.ts`：支付与结账状态口径。
- `tests/sporttery.test.ts`、`tests/orders-service.test.ts`：批量赛果及云端筛选测试。

## 现有行为

- 订单页“获取全部赛果”创建于单场赛果流程时期，当前只是循环复用 `requestMatchResult`；每场分别请求单场比分接口和让球接口，并不调用批量赛果接口。
- 投注页后来增加了 `getUniformMatchResultV1.qry` 按日期、分页批量获取赛果的实现，但订单页按钮没有随之迁移。这是两个功能加入时间不同留下的实现差异，不是接口能力限制。
- 单场“获取赛果”按钮仍适合保留单场接口，以便针对一场比赛查看比赛阶段并即时重试。
- 订单进度当前支持：已结账、未结账、已支付、未支付；默认值为“未结账”。其中“未结账”只判断 `settledAt` 为空，会同时包含未支付和已支付订单。
- 云端筛选由 `progress` 查询参数转换为 D1 条件，本地访客模式则在浏览器内按同一组字段筛选。

## 目标行为

- 订单页“获取全部赛果”改用现有按日期批量赛果接口，复用日期拆分、分页、比赛 ID 标准化和批量记录解析规则；一次合并更新页面赛果。
- 批量结果明确区分：成功、未结束或暂无赛果、已取消、请求失败；不把取消比赛伪造成比分。
- 单场“获取赛果”继续使用单场比分接口，不改变其阶段提示行为。
- 新增订单进度值“待结账”，定义为 `paymentStatus === "paid"` 且 `settledAt` 为空。
- 筛选顺序调整为：不限、未结账、待结账、已结账、已支付、未支付；默认选择“待结账”。
- 本地与云端使用相同语义；“未结账”“已支付”等原有筛选保持原含义。

## 约束与风险

- 批量赛果接口按日期范围返回数据，需要完整处理分页，并只接受当前目标比赛 ID，避免混入同日期的其它比赛。
- 订单可能跨越较长日期范围，继续按最多 30 天拆分请求；接口失败时不能覆盖已经取得的其它日期赛果。
- “待结账”由现有支付、结账字段组合得到，不需要数据库迁移或修改订单持久化结构。
- 工作区包含开发者刚调整的 Header Badge 样式和此前未提交改动，本次不得覆盖或回退。
