# 开赛提醒 Planning

日期：2026-09-14

关联 Research：`doc/planning/2026-09-11-match-start-reminder-RESEARCH.md`

## 目标

- 全局提醒未来 30 分钟内准备开赛的全部公共比赛，一场比赛在同一开赛时间下只提醒一次。
- 首次进入、公共比赛数据就绪、页面持续驻留和后台标签页恢复时检查；应用内切换投注、订单、设置不额外触发。
- 新提醒到达时先关闭尚未关闭的旧开赛提醒，再显示新批次。
- 投注页即将开赛的比赛卡片显示蓝色阴影，到达开赛时间后自动恢复现有停售样式。

## 实施方案

1. 在 `app/sporttery.ts` 抽取统一开赛时间戳解析函数，让停售判断、提醒窗口和卡片时间展示复用同一边界。
2. 新增 `app/match-start-reminder.ts` 纯函数：校验并清理本地提醒记录、筛选未来 30 分钟内尚未提醒的公共比赛、标准化并排序比赛 ID。
3. 在 `app/cloud.ts` 增加浏览器级提醒记录 key；记录格式为“标准化比赛 ID -> 本次确认的开赛时间戳”，不跟账号绑定。
4. 在 `FootballRoute` 将登录/版本阻塞层状态传给 `FootballApp`。阻塞期间关闭已有开赛提醒、不记录新比赛，解除后立即补检。
5. 在 `InnerFootballApp` 复用现有 30 秒 `saleClock`，并在标签页恢复可见时立即更新；基于 `matches + saleClock` 执行提醒检查，不依赖 `activeView`。
6. 使用受控开赛提醒 Modal 和待显示批次：初次直接打开；新批次到来而旧弹窗仍显示或关闭中时先合并到 pending，等待旧弹窗 `afterClose` 后再打开。
7. `MatchCard` 使用同一窗口纯函数增加 `starting-soon` class；CSS 为普通、已选和 hover 情况提供稳定蓝色 shadow，同时保留已选卡片左侧红色标记。
8. 增加纯函数单测，并完成 diff、全量测试、Lint、构建及桌面/移动端浏览器验证。

## 数据结构与兼容

- 新 local storage 值：`Record<string, number>`，key 为标准化比赛 ID，value 为提醒时的开赛 Unix 毫秒时间戳。
- 每次检查删除非有限值及 `kickoffAt <= now` 的记录；损坏 JSON 或旧类型安全回退为空记录。
- 窗口为 `now < kickoffAt <= now + 30 分钟`。同一批重复 ID 去重并按开赛时间、场号排序。
- 已提醒比赛延期时，原时间戳到达后记录会清理；新时间再次进入窗口时可重新提醒。
- 不新增 API、D1 字段或迁移，不修改订单、赛果和财务数据。

## 弹窗与样式

- 弹窗标题“开赛提醒”，每场显示周次场号、联赛、主客队、实际开赛时间和检测时的约剩余分钟数。
- 弹窗出现即持久化提醒记录；关闭按钮、遮罩、Esc 和“知道了”均只关闭当前提醒，不影响去重。
- 登录与强制版本刷新层级高于提醒；提醒不抢占这些阻塞流程。
- 蓝色阴影只标记当前投注页实际渲染且处于窗口内的卡片，不自动改筛选、展开分组、滚动或切换页面。

## 实施结果

- 新增统一开赛时间解析及提醒筛选纯函数，提醒记录按标准化比赛 ID 和当前开赛时间存储；过期、损坏及旧前缀数据会在检查时清理。
- 全部公共比赛数据参与提醒判断；检查由比赛数据变化、30 秒驻留时钟和标签页恢复可见触发，不依赖投注、订单、设置之间的内部切页。
- 开赛提醒使用受控弹窗和待显示批次；旧弹窗尚未关闭时发现新比赛，会先完成旧弹窗关闭动画，再显示合并后的新批次。
- 登录及版本阻塞流程优先于开赛提醒；阻塞解除后重新检查。投注页窗口内比赛卡片增加蓝色边框和阴影，到达开赛时间后由同一时钟自动移除。
