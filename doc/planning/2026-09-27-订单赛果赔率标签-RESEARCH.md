# 订单赛果赔率标签 Research

## 需求边界

- 订单卡片和订单明细中的半全场赛果 tag 不再显示“半全场”前缀，例如只显示 `负平`。
- 比分和半全场赛果如果可取得对应赔率，则显示为 `1:1 @5.23` / `负平 @6.12`。
- 本阶段仅做 Research，不开始改动业务代码。
- 附图仅用于定位订单赛果 tag，图中文字不作为开发指令。

## 相关实现

- `app/FootballApp.tsx`
  - 订单卡片和订单明细各有一处半全场 tag，当前硬编码为 `半全场 {halfFullResult}`。
  - 比分 tag 已经共用 `formatOrderScoreResult`，但比分和半全场的 tag 目前都没有赛果赔率参数。
  - 订单页“获取赛果”有单场和批量两条路径：单场主要读取比分接口，批量主要读取按日期的赛果接口；两者都没有把赔率写入 `MatchResult`。
- `app/order-model.ts`
  - `CompactOrder.selections` 只保存用户实际选中的选项及其订单赔率。
  - 如果实际赛果不是该订单已选项，订单快照中就没有该赛果选项的赔率。因此不能只从订单已选项稳定生成截图所需的两个赛果 tag。
- `app/types.ts` 与 `app/results.ts`
  - `MatchResult` 现有 `values`、全场/半场比分和让球数，没有按玩法保存赛果赔率。
  - `SavedSlip` 现有 `resultValues` 和新增的 `resultScores`，也没有按比赛/玩法持久化赛果赔率。
- `app/sporttery.ts`
  - 按日期的批量赛果接口可直接给出全场和半场比分，以及胜平负的 `h/d/a`，但不包含完整的比分和半全场赔率。
  - `getFixedBonusV1` 的 `value.matchResultList` 在完赛后返回各玩法的中奖组合、中文文案和 `odds`；`value.oddsHistory` 还保留各玩法的赔率历史。
  - 现有 `parseSportteryFixedBonus` 只解析中奖选项 ID，忽略 `matchResultList.odds`。

## 官方接口实测

2026-09-27 使用中国体育彩票官方接口对附图中的已完赛场次做了只读验证：

- 批量赛果识别到“周六006 大分三神 VS 藤枝MYFC”的比赛 ID 为 `2041711`，全场 `1:1`、半场 `0:1`。
- 该场的 fixed-bonus 返回中：
  - `CRS`：`combinationDesc = 1:1`，`odds = 5.75`；
  - `HAFU`：`combinationDesc = 负平`，`odds = 16.50`。
- 因此可以稳定构造 `1:1 @5.75` 和 `负平 @16.50`，且不依赖订单是否投注这两个中奖选项。

## 赔率口径区分

目前可用数据代表两种不同含义：

1. **订单投注赔率**：订单保存时选中选项的赔率；只有订单投注了该赛果才存在，用于订单奖金计算。
2. **官方赛果固定奖金**：完赛后 `matchResultList.odds` 给出的该玩法中奖选项赔率；即使订单未投注该项也能取得，更符合“赛果对应赔率”的展示需求。

这两个数值可能不同，不能用官方赛果赔率替换订单中的已投注赔率，也不应影响奖金计算。如按本需求展示，建议 tag 使用第 2 种，原订单选项继续使用第 1 种。

## 建议实现方向

- 扩展 fixed-bonus 赛果解析，同时返回各玩法中奖选项 ID 和对应 `odds`，仅接受有限且大于 0 的数值。
- 订单页获取赛果时，在现有比分/批量赛果之外按比赛 ID 获取 fixed-bonus 赛果赔率；赔率获取失败时不阻断赛果判定，只省略 `@...`。
- 在 `MatchResult` 与订单 JSON 中新增可选的按比赛/玩法赔率映射，与 `resultValues` 一起写入，确保页面刷新、云端同步和历史查看后仍然一致。
- 展示函数统一组合“赛果文案 + 两位小数赔率”：
  - 普通比分：`1:1 @5.75`；
  - 其他比分：`胜其他 6:0 @250.00`（具体比分仍使用 `resultScores`）；
  - 半全场：`负平 @16.50`，不再显示“半全场”。
- 数据继续保存在 `user_orders.data_json`，不需要 D1 表迁移；新字段必须为可选，保持旧订单兼容。

## 风险与兼容

- 批量赛果不含比分/半全场的完整赔率，若要全面显示，需要为每场已完赛比赛增加一次 fixed-bonus 请求。应沿用现有请求去重和限速，避免订单批量判定瞬间放大官方接口压力。
- 仅在 React 页面上从当前比赛缓存查赔率不够稳定：缓存只保留有限天数，页面刷新或跨设备后可能丢失，而且不一定是官方最终赛果赔率。
- 已经保存赛果的历史订单不会自动进入现有“待获取赛果”列表，因此新字段不会自动补齐。若要补历史赔率，需要另外设计重新获取与回写流程。
- 手动填写赛果时没有官方赔率数据；除非同时成功获取 fixed-bonus，否则只显示赛果文案。

## 预计验证范围

- 解析测试：fixed-bonus 中普通比分、三种“其他”比分和九种半全场返回正确选项 ID 与赔率；无效赔率不写入。
- 赛果测试：赔率请求成功时跟随赛果保存，请求失败时仍能完成判定。
- 模型/服务测试：新赔率映射经 `SavedSlip <-> CompactOrder` 和云端批量更新不丢失，旧订单仍能通过验证。
- 文案测试：有赔率时保留两位小数，无赔率时不显示 `@`，半全场不显示前缀。
- 完整验证：`npm test`、`npm run lint`、`npm run build`，并用桌面端和移动端浏览器同时检查订单卡片与明细抽屉。
